# 一、先看痛：不分层会怎样

假设你有 20 个接口要测，每个都这么写：

```python
def test_login():
    url = "http://127.0.0.1:5000/api/login"
    resp = requests.post(url, json={"username": "admin", "password": "123456"})
    assert resp.json()["code"] == 0

def test_get_user():
    url = "http://127.0.0.1:5000/api/user/1"
    headers = {"token": "mock_token_abc123"}
    resp = requests.get(url, headers=headers)
    assert resp.json()["code"] == 0

# ... 还有 18 个
```

问题：

| 问题 | 后果 |
|---|---|
| 地址写死 20 遍 | 换个环境要改 20 处 |
| token 每个用例手动加 | token 逻辑一改，全崩 |
| 没有日志 | 失败了不知道请求了什么 |
| 没有统一的超时 | 一个接口卡死，全部挂 |
| 断言满天飞 | 失败信息全靠猜 |
| 加个"所有请求带签名" | 改 20 处 |

**框架做的事情，就是把"变的东西"和"不变的东西"分开。**

# 二、分层设计

```
framework/
├── config/              配置层：地址、超时、环境
│   ├── config.yaml         ← 环境参数（改环境只动这里）
│   └── config.py           ← 读取配置的代码
│
├── common/              公共层：跟业务无关的工具
│   ├── logger.py           ← 日志
│   ├── yaml_util.py        ← 读写 YAML
│   ├── var_pool.py         ← 变量池（解决接口依赖）
│   ├── request_util.py     ← 请求封装（日志/超时/变量替换）
│   ├── assert_util.py      ← 断言封装
│   └── case_runner.py      ← 用例执行引擎（核心）
│
├── api/                 业务层：每个模块一个类
│   ├── base_api.py         ← 父类，封装公共能力
│   ├── user_api.py         ← 用户模块
│   └── order_api.py        ← 订单模块
│
├── data/                数据层：用例数据
│   ├── test_login.yaml
│   ├── test_order.yaml
│   └── test_user.yaml
│
├── testcases/           用例层：只负责"跑"
│   ├── test_login.py          ← YAML 数据驱动
│   ├── test_order.py
│   ├── test_user.py
│   └── test_api_style.py     ← 复杂逻辑用 Python 写
│
├── conftest.py          全局 fixture + 命令行参数（放根目录才对所有用例生效）
├── run.py               入口：一条命令跑全部
└── pytest.ini
```

## 为什么要这么分

**一句话原则：改一个东西，只需要动一个地方。**

| 变化场景 | 只改哪里 |
|---|---|
| 换测试环境（test → prod） | `config.yaml` |
| 所有请求加 3 秒超时 | `request_util.py` |
| 加新的断言方式 | `assert_util.py` |
| 新增一个用户接口 | `user_api.py` |
| 加一条登录用例 | `data/test_login.yaml`（**不用写代码**） |

**最后一条是分层的终极目标**：加用例不用写代码。

# 三、逐层实现

## 3.1 配置层

```yaml
# config/config.yaml
default_env: test

test:
  base_url: http://127.0.0.1:5000
  timeout: 10
prod:
  base_url: https://api.example.com
  timeout: 30
```

```python
# config/config.py
class Config:
    def __init__(self, env=None):
        self.env = env or self._default_env()
        conf = self._load()[self.env]
        self.base_url = conf["base_url"]
        self.timeout = conf["timeout"]
```

**为什么要有这一层**：环境地址散落在用例里，是最常见的坏味道。
面试时说"我把环境配置抽出来了，切换环境只改一个 yaml"，是及格线。

## 3.2 日志层

```python
# common/logger.py
import logging

def get_logger(name="autotest"):
    logger = logging.getLogger(name)
    logger.setLevel(logging.INFO)
    ...
    return logger
```

**关键点**：
- 同时输出到文件和控制台
- 日志要带时间、级别、文件名行号
- 按天切分，避免单个文件无限增大

> 面试考点：日志为什么重要？
> 自动化的价值在于**无人值守跑完后能定位问题**。
> 用例在半夜挂了，你早上来只能看日志。没有日志的框架等于白跑。

## 3.3 变量池

解决接口依赖（Day 2 讲过，这里做成模块）：

```python
# common/var_pool.py
class VarPool:
    _vars = {}

    @classmethod
    def set(cls, key, value):
        cls._vars[key] = value

    @classmethod
    def replace(cls, data):
        """把 ${key} 换成真实值，整串占位符时保留类型"""
        ...
```

**为什么用类变量（类属性）**：全局唯一，任何地方 set 了，别的地方都能 get 到。
这是"单例"思想的最简实现。

## 3.4 请求封装（核心）

```python
# common/request_util.py
class RequestClient:
    def __init__(self):
        self.session = requests.Session()
        self.config = get_config()
        self.log = get_logger()

    def send(self, method, path, **kwargs):
        # 1 变量替换
        kwargs = VarPool.replace(kwargs)
        # 2 拼 URL
        url = self.config.base_url + path
        # 3 默认超时
        kwargs.setdefault("timeout", self.config.timeout)
        # 4 发请求 + 记日志
        self.log.info(f"请求：{method} {url}，参数 {kwargs}")
        resp = self.session.request(method, url, **kwargs)
        self.log.info(f"响应：{resp.status_code} {resp.text[:500]}")
        # 5 异常处理
        ...
        return resp
```

**这层是整个框架的心脏**。所有"统一处理"都在这里：超时、日志、变量替换、异常处理、重试。

## 3.5 断言封装

不要用裸 `assert`，封装成这样，失败信息才有意义：

```python
# common/assert_util.py
def assert_eq(actual, expected, msg=""):
    assert actual == expected, f"断言失败：期望 {expected}，实际 {actual}。{msg}"

def assert_contains(container, item, msg=""):
    assert item in container, f"断言失败：{container} 中不包含 {item}。{msg}"
```

更进一步：支持从响应里用 JSONPath 取值再断言（数据驱动需要）。

## 3.6 用例执行引擎（最关键）

这是"数据驱动"能成立的核心：

```python
# common/case_runner.py
def run_case(client, case):
    """
    case 是一条 YAML 里读出来的字典：
      name     用例名
      request  请求信息（method/path/json...）
      extract  要提取的变量
      validate 断言列表
    """
    # 1 发请求（method / path 单独取出来，其余原样透传给 requests）
    req = copy.deepcopy(case["request"])
    resp = client.send(req.pop("method"), req.pop("path"), **req)

    # 2 提取变量（给后面的用例用）
    for var_name, expr in case.get("extract", {}).items():
        VarPool.set(var_name, extract_by_jsonpath(resp.json(), expr))

    # 3 断言
    for item in case.get("validate", []):
        do_assert(resp, item)
```

然后用例文件就变成这样：

```python
# testcases/test_login.py
cases = load_yaml("data/test_login.yaml")

@pytest.mark.parametrize("case", cases, ids=[c["name"] for c in cases])
def test_login(case):
    run_case(client, case)
```

**加一条用例 = 往 YAML 里加一段，不用写一行 Python。**

这就是面试官最想听到的："我的用例是数据驱动的，业务同事也能加用例。"

## 3.7 业务层（继承）

```python
# api/base_api.py
class BaseAPI:
    """父类：持有 client，提供通用能力"""
    def __init__(self, client=None):
        self.client = client or get_client()

# api/user_api.py
class UserAPI(BaseAPI):
    def login(self, username, password):
        return self.client.post("/api/login",
                                json={"username": username, "password": password})
```

**两种写法并存**：
- 简单场景：直接用 YAML 数据驱动
- 复杂场景（要做逻辑判断、循环、特殊处理）：写 Python 代码，用 api 层

成熟的框架两种都支持。面试时能说出"什么时候用哪种"，说明你有实战感。

# 四、数据驱动：用例长什么样

```yaml
# data/test_login.yaml
- name: 登录成功
  request:
    method: POST
    path: /api/login
    json:
      username: admin
      password: "123456"
  extract:
    token: $.data.token
  validate:
    - eq: [$.code, 0]
    - eq: [$.data.username, admin]

- name: 密码错误
  request:
    method: POST
    path: /api/login
    json:
      username: admin
      password: wrong
  validate:
    - eq: [$.code, 1003]
```

字段含义：

| 字段 | 作用 |
|---|---|
| `name` | 用例名，显示在报告里 |
| `request` | 请求信息，直接对应 requests 的参数 |
| `extract` | 提取响应字段存进变量池（解决接口依赖） |
| `validate` | 断言列表，`eq` 相等、`contains` 包含、`ne` 不等 |

**依赖示例**：下单用例用上一个用例提取的用户 id

```yaml
- name: 下单
  request:
    method: POST
    path: /api/order
    json:
      userId: ${user_id}      # ← 自动替换成真实值
      amount: 99.9
  validate:
    - eq: [$.code, 0]
```

## 为什么 `-n` 并发用不了（这一条要讲透）

这是整套课程里最值得深挖的一个设计取舍，面试也常问。

**事实先摆出来**，你自己复现一遍：

```bash
cd day04-搭建框架/framework
pytest -n 2
```

框架会在开头提示你「`-n` 已被忽略，按串行执行」，用例照常跑完，不会让你看到一屏 `KeyError`。

（这里还踩过一个坑：最初是在 `pytest_configure` 里 `print` 一长段说明，结果那段话被重复输出了 62 遍——
那个阶段 pytest 的捕获机制已经介入，往 stdout/stderr 写长文本会被反复回显。
后来改成用 pytest 官方的 `pytest_report_header` 钩子输出，由 pytest 自己打印，才只出现一次。）

### 为什么拦

`pytest-xdist` 的 `-n` 不是"开线程"，是**开进程**。每个 worker 是独立的 Python 进程，有各自的内存空间。

而这个框架解决接口依赖靠的是 `VarPool` 全局变量池：

```
用例 A：创建订单 → 从响应提取 orderId = 1001 → VarPool.set("order_id", 1001)
用例 B：读 ${order_id} → VarPool.get("order_id")
```

单进程串行时，A 先跑、B 后跑，变量池里有序号，没问题。

`-n 2` 之后，A 可能落在 worker1，B 可能落在 worker2。**两个进程各有各的变量池**，worker2 里压根没有 `order_id`：

```
KeyError: 变量 ${order_id} 不在变量池中
```

**这不是 bug，是架构决定的。** 任何"靠进程内全局变量传数据"的框架，都不可能直接支持多进程并发。

### 要支持并发，得改数据传递方式

| 方案 | 做法 | 代价 |
|---|---|---|
| fixture 传值 | 上游用例返回数据，下游通过 fixture 依赖拿到 | 用例之间耦合变强 |
| 外部存储 | 变量写到文件 / Redis，各进程读同一份 | 引入外部依赖，要处理并发读写 |
| **用例自包含** | 每条用例自己造数据，不依赖上游 | 最彻底，代价是重复请求 |

成熟框架通常用**第三条打底 + 第一条补漏**：尽量让用例自包含；实在需要跨模块的组合场景（比如"建用户 → 下单 → 支付"），就写成**同一条用例**，而不是拆成两条靠变量池串起来。

**`testcases/test_api_style.py::test_full_business_flow` 就是这个做法** —— 把整条链路写在一个函数里，从头到尾自己造数据、自己清理（`finally` 里删用户）。所以它天生是并发安全的。你可以把两个文件对着看一次，这一对比比读十页文档管用。

> **面试怎么答这题**（答好了很加分）：
> "我的框架用全局变量池解决接口依赖，好处是数据驱动的用例写起来简单，`${}` 占位就行。
> 但代价是不能直接上 `pytest-xdist` —— xdist 是多进程，进程间内存不共享，变量池传不过去。
> 我现在的做法是：单接口用例走 YAML 数据驱动，跨模块的完整链路写成一条自包含的代码用例。
> 要真上并发，得把变量池换成外部存储（文件 / Redis），或者把用例改造成完全不依赖上游数据。"

# 七、【面试考点】框架设计（最重要）

**Q1：你的框架是怎么分层的？为什么这么分？**

> 分五层：配置层、公共工具层、业务 API 层、用例数据层、用例执行层。
> 原则是"改一个东西只动一个地方"：
> 换环境只改 config.yaml，加超时只改 request_util，加用例只改 YAML 不用写代码。
> 公共能力（日志、超时、变量替换、异常处理）全部收敛到请求封装层，业务层只关心接口路径和参数。

**Q2：用例数据怎么组织的？**

> YAML 文件，一个模块一个文件。每条用例包含 name / request / extract / validate 四部分。
> 用 pytest 的 parametrize 把 YAML 读进来生成用例。
> 好处是加用例不用写代码，业务测试的同事也能维护；坏处是复杂逻辑（循环、条件判断）不好表达，
> 这种场景我就写 Python 用例，两种方式是共存的。

**Q3：接口依赖怎么解决？**

> 三层机制：① 用例里用 `${变量名}` 占位；
> ② 上游用例通过 `extract` 字段用 JSONPath 提取响应字段存进全局字典；
> ③ 发请求前统一做替换。
> 这里有个坑：整串是占位符时要保留原类型，否则 int 的 userId 变成字符串 "5"，服务端匹配不上。

**Q4：怎么保证用例之间不互相影响？**

> ① 每条用例自己准备数据（用 fixture 造临时数据，用完在 teardown 删掉）
> ② 公共数据（token）用 session 级 fixture，只读不写
> ③ 尽量不依赖执行顺序——这是最重要的，因为将来上并发（xdist 是多进程）时，有顺序依赖就会乱。
> 但我要诚实说：本框架目前还用全局变量池在用例之间传接口依赖，
> 所以还不能直接上 `-n`——框架检测到 `-n` 会自动忽略它、退化成串行执行；
> 要真正并发，得先把依赖数据挪到外部存储或改成用例自包含。

**Q5：你的框架有没有接 CI？**

> 用 Jenkins，配 Git webhook 或者定时任务，拉代码 → 装依赖 → 跑 pytest → 出报告 → 失败发钉钉。
> 提交代码时只跑冒烟标记（`-m smoke`），全量放晚上跑。
> （Day 5 详细讲）

**Q6：遇到过什么技术难点？**

挑一个真实的说，比如：
> 接口依赖的类型问题——替换后数字变字符串导致服务端匹配失败，排查了很久，
> 最后在替换函数里区分"整串占位符"和"部分占位符"才解决。
> 或者：用例之间脏数据互相干扰，后来加了 fixture teardown 自动清理 + 每条用例用独立数据。

**诚实提醒**：讲难点时不要编。没遇到过就说"目前框架比较简单，主要在解决 XX 问题"，
然后说出你的判断。编造的细节一追问就露。

**Q7：你的框架还有什么不足？**（这题几乎是必问，答不上来减分）

诚实说，然后说改进方向：
> 目前没有做数据库校验，复杂业务的落库验证还得手工查；
> 报告用的是 pytest-html，没有 Allure 的趋势分析和历史对比；
> **最要紧的是并发上不去**——框架用全局变量池传接口依赖，而 xdist 是多进程、
> 内存不共享，所以现在传 `-n` 会被框架自动忽略、退化成串行，用例多的时候跑得慢。
> 要支持并发，得把变量池换成外部存储，或者把用例改造成自包含，这是下一步要做的。

**能说出自己的不足，反而说明你真的做过。**
