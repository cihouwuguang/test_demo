# Day 4 · 搭建自己的自动化框架

> **这是 5 天里最重要的一天。**
> 面试时，"你的框架怎么设计的"比任何八股文都重要。
> 今天的目标不是"能跑"，是**能讲清楚每一层为什么这么设计**。

---

# 一、先看痛：不分层会怎样

假设你有 20 个接口要测，每个都这么写：

```python
def test_login():
    url = "http://127.0.0.1:5000/api/login"
    resp = requests.post(url, json={"username": "admin", "password": "123456"})
    assert resp.json()["code"] == 0

def test_get_user():
    url = "http://127.0.0.1:5000/api/user/1"
    headers = {"token": "mock_token_abc123"}
    resp = requests.get(url, headers=headers)
    assert resp.json()["code"] == 0

# ... 还有 18 个
```

问题：

| 问题 | 后果 |
|---|---|
| 地址写死 20 遍 | 换个环境要改 20 处 |
| token 每个用例手动加 | token 逻辑一改，全崩 |
| 没有日志 | 失败了不知道请求了什么 |
| 没有统一的超时 | 一个接口卡死，全部挂 |
| 断言满天飞 | 失败信息全靠猜 |
| 加个"所有请求带签名" | 改 20 处 |

**框架做的事情，就是把"变的东西"和"不变的东西"分开。**

# 二、分层设计

```
framework/
├── config/              【第 1 层】配置层：地址、超时、环境
│   ├── config.yaml         ← 环境参数（改环境只动这里）
│   └── config.py           ← 读取配置的代码
│
├── common/               【第 2、3 层】公共能力
│   ├── logger.py           ┐
│   ├── yaml_util.py        ├ 第 2 层 公共工具：跟业务无关，任何地方都能用
│   ├── var_pool.py         ┘
│   ├── request_util.py     ← 第 3 层 请求封装（整个框架的心脏）
│   ├── assert_util.py      ← 断言封装
│   └── case_runner.py      ← 用例执行引擎（数据驱动的核心）
│
├── api/                 【第 4 层】业务 API 层：每个模块一个类
│   ├── base_api.py         ← 父类，封装公共能力
│   ├── user_api.py         ← 用户模块
│   └── order_api.py        ← 订单模块
│
├── data/                【第 5 层】用例数据层：用例写在 YAML 里
│   ├── test_login.yaml
│   ├── test_order.yaml
│   └── test_user.yaml
│
├── testcases/           【第 5 层】用例入口：只负责"把 data 里的用例跑起来"
│   ├── test_login.py          ← YAML 数据驱动
│   ├── test_order.py
│   ├── test_user.py
│   └── test_api_style.py     ← 复杂逻辑用 Python 写
│
├── unit/                common 层纯函数的单元测试（不需要 mock 服务）
│   └── test_common.py
│
├── conftest.py          全局 fixture + 命令行参数（放根目录才对所有用例生效）
├── run.py               入口：一条命令跑全部
└── pytest.ini
```

**五层是这么分的**（后面 Q1、话术里都用这一套说法，别混）：

| 层 | 目录 | 职责 |
|---|---|---|
| 1 配置层 | `config/` | 环境地址、超时、请求头；换环境只改一个文件 |
| 2 公共工具层 | `common/` 里的 logger / yaml_util / var_pool | 跟业务无关的工具函数 |
| 3 请求封装层 | `common/request_util.py` | 变量替换、拼 URL、默认超时、日志、异常、重试——**统一处理都收敛在这** |
| 4 业务 API 层 | `api/` | 每个模块一个类，只写接口路径和业务参数 |
| 5 用例数据层 | `data/` + `testcases/` | 用例数据在 YAML 里，`testcases/` 只负责把它跑起来 |

## 为什么要这么分

**一句话原则：改一个东西，只需要动一个地方。**

| 变化场景 | 只改哪里 |
|---|---|
| 换测试环境（test → prod） | `config.yaml` |
| 所有请求加 3 秒超时 | `request_util.py` |
| 加新的断言方式 | `assert_util.py` |
| 新增一个用户接口 | `user_api.py` |
| 加一条登录用例 | `data/test_login.yaml`（**不用写代码**） |

**最后一条是分层的终极目标**：加用例不用写代码。

# 三、逐层实现

## 3.1 配置层

```yaml
# config/config.yaml
default_env: test

test:
  base_url: http://127.0.0.1:5000
  timeout: 10
prod:
  base_url: https://api.example.com
  timeout: 30
```

```python
# config/config.py
class Config:
    def __init__(self, env=None):
        self.env = env or self._default_env()
        conf = self._load()[self.env]
        self.base_url = conf["base_url"]
        self.timeout = conf["timeout"]
```

**为什么要有这一层**：环境地址散落在用例里，是最常见的坏味道。
面试时说"我把环境配置抽出来了，切换环境只改一个 yaml"，是及格线。

## 3.2 日志层

```python
# common/logger.py
import logging

def get_logger(name="autotest"):
    logger = logging.getLogger(name)
    logger.setLevel(logging.INFO)
    ...
    return logger
```

**关键点**：
- 同时输出到文件和控制台
- 日志要带时间、级别、文件名行号
- 按天切分，避免单个文件无限增大

> 面试考点：日志为什么重要？
> 自动化的价值在于**无人值守跑完后能定位问题**。
> 用例在半夜挂了，你早上来只能看日志。没有日志的框架等于白跑。

## 3.3 变量池

解决接口依赖（Day 2 讲过，这里做成模块）：

```python
# common/var_pool.py
class VarPool:
    _vars = {}

    @classmethod
    def set(cls, key, value):
        cls._vars[key] = value

    @classmethod
    def replace(cls, data):
        """把 ${key} 换成真实值，整串占位符时保留类型"""
        ...
```

**为什么用类变量（类属性）**：全局唯一，任何地方 set 了，别的地方都能 get 到。
这是"单例"思想的最简实现。

## 3.4 请求封装（核心）

```python
# common/request_util.py
class RequestClient:
    def __init__(self):
        self.session = requests.Session()
        self.config = get_config()
        self.log = get_logger()

    def send(self, method, path, **kwargs):
        # 1 变量替换
        kwargs = VarPool.replace(kwargs)
        # 2 拼 URL
        url = self.config.base_url + path
        # 3 默认超时
        kwargs.setdefault("timeout", self.config.timeout)
        # 4 发请求 + 记日志
        self.log.info(f"请求：{method} {url}，参数 {kwargs}")
        resp = self.session.request(method, url, **kwargs)
        self.log.info(f"响应：{resp.status_code} {resp.text[:500]}")
        # 5 异常处理
        ...
        return resp
```

**这层是整个框架的心脏**。所有"统一处理"都在这里：超时、日志、变量替换、异常处理、重试。

## 3.5 断言封装

不要用裸 `assert`，封装成这样，失败信息才有意义：

```python
# common/assert_util.py
def assert_eq(actual, expected, msg=""):
    assert actual == expected, f"断言失败：期望 {expected}，实际 {actual}。{msg}"

def assert_contains(container, item, msg=""):
    assert item in container, f"断言失败：{container} 中不包含 {item}。{msg}"
```

更进一步：支持从响应里用 JSONPath 取值再断言（数据驱动需要）。

## 3.6 用例执行引擎（最关键）

这是"数据驱动"能成立的核心：

```python
# common/case_runner.py
def run_case(client, case):
    """
    case 是一条 YAML 里读出来的字典：
      name     用例名
      request  请求信息（method/path/json...）
      extract  要提取的变量
      validate 断言列表
    """
    # 1 发请求（method / path 单独取出来，其余原样透传给 requests）
    req = copy.deepcopy(case["request"])
    resp = client.send(req.pop("method"), req.pop("path"), **req)

    # 2 提取变量（给后面的用例用）
    for var_name, expr in case.get("extract", {}).items():
        VarPool.set(var_name, extract_by_jsonpath(resp.json(), expr))

    # 3 断言
    for item in case.get("validate", []):
        do_assert(resp, item)
```

然后用例文件就变成这样：

```python
# testcases/test_login.py
cases = load_yaml("data/test_login.yaml")

@pytest.mark.parametrize("case", cases, ids=[c["name"] for c in cases])
def test_login(case):
    run_case(client, case)
```

**加一条用例 = 往 YAML 里加一段，不用写一行 Python。**

这就是面试官最想听到的："我的用例是数据驱动的，业务同事也能加用例。"

## 3.7 业务层（继承）

```python
# api/base_api.py
class BaseAPI:
    """父类：持有 client，提供通用能力"""
    def __init__(self, client=None):
        self.client = client or get_client()

# api/user_api.py
class UserAPI(BaseAPI):
    def login(self, username, password):
        return self.client.post("/api/login",
                                json={"username": username, "password": password})
```

**两种写法并存**：
- 简单场景：直接用 YAML 数据驱动
- 复杂场景（要做逻辑判断、循环、特殊处理）：写 Python 代码，用 api 层

成熟的框架两种都支持。面试时能说出"什么时候用哪种"，说明你有实战感。

# 四、数据驱动：用例长什么样

```yaml
# data/test_login.yaml
- name: 登录成功
  request:
    method: POST
    path: /api/login
    json:
      username: admin
      password: "123456"
  extract:
    token: $.data.token
  validate:
    - eq: [status_code, 200]        # 第一层：HTTP 状态码
    - eq: [$.code, 0]               # 第二层：业务 code
    - eq: [$.data.username, admin]

- name: 密码错误
  request:
    method: POST
    path: /api/login
    json:
      username: admin
      password: wrong
  validate:
    - eq: [status_code, 200]
    - eq: [$.code, 1003]
```

字段含义：

| 字段 | 必填 | 作用 |
|---|---|---|
| `name` | ✅ | 用例名，显示在报告里 |
| `request` | ✅ | 请求信息（必须含 `method` / `path`），其余 key 直接对应 requests 的参数 |
| `extract` | — | 提取响应字段存进变量池（解决接口依赖） |
| `validate` | ✅ | 断言列表，**不能为空** |

**断言算子一览**（`assert_util.py` 里的 `ASSERT_MAP`）：

| 算子 | 参数 | 说明 |
|---|---|---|
| `eq` / `ne` | `[实际值表达式, 期望值]` | 相等 / 不等 |
| `contains` / `not_contains` | `[实际值表达式, 期望值]` | 包含 / 不包含 |
| `gt` / `lt` | `[实际值表达式, 期望值]` | 大于 / 小于 |
| `is_null` / `not_null` | `[实际值表达式]` | 为空 / 不为空（**只 1 个参数**） |
| `approx` | `[实际值表达式, 期望值]` | 近似相等（容差 0.01），**金额用这个，不要用 `eq`** |

实际值表达式有两种写法：
- `status_code` → 取 HTTP 状态码
- `$.xxx` → 用 JSONPath 从响应体里取

> ### ⚠️ 框架会帮你拦住的四种"假绿"
>
> 这套框架的卖点是"加用例只改 YAML、不用写代码"，自由度很高。
> 但**自由度没有校验兜底，就是假绿的温床**。所以 `case_runner.validate_case()`
> 会在每条用例执行前校验结构，下面这些情况**直接报错，不会判通过**：
>
> | 情况 | 以前会发生什么 | 现在 |
> |---|---|---|
> | 漏写 `validate` 字段 | 零断言执行 → 报告里一条绿的 `passed` | 报错，指出缺少必填字段 |
> | `validate` 拼成 `validates` | 同上，**一个字母的差别** | 报错，指出未知字段 |
> | `validate` 写成空列表 | 同上 | 报错 |
> | `request` 缺 `method`/`path` | 运行到一半才炸 | 报错 |
> | JSONPath 路径写错（如 `$.data.tokenn`） | `is_null` 会"通过"、`ne` 会**恒真通过** | 报错「路径未匹配」，且和「值为 null」严格区分 |
> | `extract` 提不到值 | 只打一条 WARNING，用例仍判**通过**，错误跑到下游才炸 | 报错，指出提取失败 |
> | 服务端返回 500 + HTML | 抛 `JSONDecodeError`，看起来像"框架崩了" | 干净的断言失败，并打印状态码和响应体片段 |
>
> 这些不是"额外加的保险"，而是**测试框架的底线**：
> 一条用例如果没有断言，它就没有存在价值；一个写错的断言，比没有断言更危险。

**依赖示例**：下单用例用 conftest 里准备的测试用户 id

```yaml
- name: 下单
  request:
    method: POST
    path: /api/order
    json:
      userId: "${test_user_id}"   # ← 自动替换成真实值
      amount: 99.9
  validate:
    - eq: [status_code, 200]
    - eq: [$.code, 0]
```

> ⚠️ **变量名别猜。** 这里的 `test_user_id` 是 `conftest.py` 里
> `VarPool.set("test_user_id", user_id)` 设进去的（全局前置创建的测试用户）。
> 变量池里**没有** `user_id` 这个名字，写 `${user_id}` 会直接
> `KeyError: 变量 ${user_id} 不在变量池中` —— 而报错信息会把锅甩给变量池，
> 让你以为是框架的问题。**变量池里现在有哪些变量，看日志里的
> `变量 ${xxx} 不在变量池中，当前已有：[...]` 后半句。**

可用的变量有两个来源：

| 变量 | 谁放进去的 | 什么时候可用 |
|---|---|---|
| `token` | `conftest.py` 全局前置（登录后） | 全部用例 |
| `test_user_id` | `conftest.py` 全局前置（创建测试用户后） | 全部用例 |
| 你自己 `extract` 的变量 | 同文件里**前面**的用例 | 该用例之后 |

# 五、跑起来

```bash
cd day04-搭建框架/framework

# 跑全部（接口用例 + 单元测试），出 HTML 报告
python run.py

# 或者直接用 pytest
pytest -vs

# 只跑冒烟
pytest -m smoke

# 只跑 common 层纯函数的单元测试（**不需要 mock 服务**）
pytest unit/ -v

# 只跑接口用例
pytest testcases/ -v

# 出 HTML 报告
pytest --html=report.html --self-contained-html
```

> **为什么要专门有 `unit/` 这个目录？**
> 这套课的主题是"怎么测"，而 `common/` 下的东西全是**最适合被单测的纯函数**：
> 变量替换、JSONPath 取值、断言算子、用例结构校验。
> 一个教测试的项目自己不做单测，说服力直接归零。
> 而且这些单测守的不是"功能有没有"，是**上面那四种假绿路径有没有被重新打开**——
> 比如你哪天把 `validate_case` 的未知字段校验删了，`pytest unit/` 会立刻红。

# 六、还能加什么（面试加分项）

| 能力 | 怎么做 | 面试价值 | 本框架现状 |
|---|---|---|---|
| 失败重试 | `pytest --reruns 2` | 处理环境抖动 | ⚠️ 见下方说明：传输层重试**已实现**，用例级重试**不建议开** |
| 并发执行 | `pytest -n 4` | 用例多时提速 | ⚠️ 不支持，检测到会降级并提示（原因见下） |
| Allure 报告 | `allure-pytest` + `allure serve` | 报告漂亮，趋势图 | ❌ 未接，当前用 pytest-html（**没做就说没做**） |
| 数据库校验 | 封装 `db_util.py`，断言时支持 `db_check` | 金融业务必备 | ❌ 未做 |
| 钉钉/邮件通知 | Jenkins 配插件 | CI 闭环 | ❌ 未做（仓库里没有 CI 配置） |
| 接口自动导入 | 读 Swagger/OpenAPI 生成 YAML | 提效，很加分 | ❌ 未做 |
| 数据清理 | fixture teardown 或专门的清理脚本 | 避免脏数据 | ✅ 已做（`conftest.py` 的 `prepare`，含兜底清理） |
| 自定义命令行参数 | `pytest --env=prod` | 灵活切换环境 | ✅ 已做 |
| 字段/结构校验 | 用例 schema 校验 | 防止假绿 | ✅ 已做（`validate_case`） |

**面试时挑 2-3 个说**，说清楚"为什么加"和"怎么实现的"，比列一堆名词强。
**没实现的就直说没实现**——说"我计划这么做，因为 XX"，比吹成"已经做了"安全得多。

### 关于「失败重试」的两个坑（别讲错）

第一，**框架里已经有重试了，只是重试的层次不同**：

`common/request_util.py` 的 `send(method, path, retry=0, **kwargs)` 实现了**传输层重试**——
只捕获 `Timeout` 和 `ConnectionError` 这两类"网络抖了一下"的异常，**重试期间不重复发成功的请求**。
它**不覆盖断言失败**，也**不覆盖 HTTP 4xx/5xx**（那是业务结果，重试没有意义）。

第二，**写操作重试是危险的**：

`requirements.txt` 里装了 `pytest-rerunfailures`，但**这个框架恰恰不能安全地开用例级重试**——
重试一条"支付订单"用例，意味着**可能发生重复支付**。
真要开，只能给幂等、只读的用例打标记再加 `--reruns`：

```bash
# 只对标记过的用例重试，绝不无差别 --reruns
pytest --reruns 2 --reruns-delay 1 -m retryable
```

> 面试时的加分说法：
> "重试我会分两层看：传输层的超时/连接错误可以自动重试，因为请求没到服务端；
> 但业务层的重试要看接口幂等性——支付、下单这类写操作我不会盲目重试，
> 会用幂等键或者先在测试环境确认状态。"

## 为什么 `-n` 并发用不了（这一条要讲透）

这是整套课程里最值得深挖的一个设计取舍，面试也常问。

### 先把事实摆清楚（都可以自己复现）

```bash
cd day04-搭建框架/framework

# ① 默认：检测到 -n 会【降级为串行】，用例照常跑完
pytest -n 2
#   → 开头一行提示 + 结尾一个醒目的提示块
#   → 78 passed，**退出码 0**

# ② 想让它在 CI 上直接失败（推荐 CI 用这个）
pytest -n 2 --strict-parallel
#   → 直接报错退出，退出码 1
```

**⚠️ 一句话记住**：默认行为是「**带提示的降级**」，**不是「直接失败」**。

> 这里踩过两个坑，都值得记：
>
> **坑一（输出方式）**：最初是在 `pytest_configure` 里 `print` 一长段说明，
> 结果那段话被重复输出了 62 遍——那个阶段 pytest 的捕获机制已经介入，
> 往 stdout/stderr 写长文本会被反复回显。后来改成用官方的
> `pytest_report_header` 钩子输出，由 pytest 自己打印，才只出现一次。
>
> **坑二（静默降级更危险）**：只提示一次还不够。实测时发现——
> 如果提示只出现在开头，很容易被后面几百行用例输出刷掉；
> 更麻烦的是**退出码是 0**，所以 CI 里配了 `-n 4`，构建是绿的，
> 却没人知道并发压根没生效。**这比"直接失败"危险得多**——失败至少会有人来看。
> 所以现在做了三件事让降级不再静默：
> ①报告头提示 ②结尾再用分隔块提示一次 ③提供 `--strict-parallel` 让 CI 选择直接失败。

### 为什么拦

`pytest-xdist` 的 `-n` 不是"开线程"，是**开进程**。每个 worker 是独立的 Python 进程，有各自的内存空间。

而这个框架解决接口依赖靠的是 `VarPool` 全局变量池：

```
用例 A：创建订单 → 从响应提取 orderId = 1001 → VarPool.set("order_id", 1001)
用例 B：读 ${order_id} → VarPool.get("order_id")
```

单进程串行时，A 先跑、B 后跑，变量池里有序号，没问题。

`-n 2` 之后，A 可能落在 worker1，B 可能落在 worker2。**两个进程各有各的变量池**，worker2 里压根没有 `order_id`：

```
KeyError: 变量 ${order_id} 不在变量池中
```

**这不是 bug，是架构决定的。** 只要靠"进程内全局变量"在用例之间传数据，默认的 `load` 调度下就一定会崩。

### ⚠️ 但不要说"任何框架都不可能" —— 这句话会被反将

在**副本**里去掉 conftest 的拦截（模拟"如果不禁用并发"），实测结果很有意思：

```
pytest -n 2                                  → 78 passed   ← 侥幸，见下
pytest -n 3                                  → 4 failed
pytest -n 4                                  → 4 failed
pytest -n 8                                  → 4 failed
pytest -n 2 --dist=load --maxschedchunk=1     → 2 failed    ← 稳定复现失败
pytest -n 2 --dist=loadscope                 → 78 passed   ← 真并发
pytest -n 2 --dist=loadfile                  → 78 passed   ← 真并发
```

**为什么 `-n 2` 会"侥幸通过"？** 这比"稳定失败"更值得讲：

xdist 的默认 `load` 调度不是"一条一条轮流发"，而是**分块**发给各 worker。
当前共 78 条用例、2 个 worker 时，切分点**恰好**落在文件边界上——
`test_order.yaml` 的 10 条用例整块落进了同一个 worker，依赖自然就保住了。
worker 数一换成 3/4/8，切分点挪进文件中间，立刻变成 `4 failed`。

**也就是说：它能不能跑通，取决于切分点落在哪。**

`--maxschedchunk=1` 强制"一条一条发"，就稳定失败了；
`loadscope`（按模块分组）/ `loadfile`（按文件分组）则因为**依赖都收敛在单文件内**而稳定通过。

**但这也是脆弱的巧合**：依赖一旦跨文件（比如 A 文件创建、B 文件查询），`loadscope` 也会崩。

所以准确的讲法是：

> 默认的 `load` 调度**不保证**同一文件的用例落在同一个进程里，依赖随时可能断——
> 表现是**时好时坏**，这比稳定失败更糟，因为你会以为"没问题"。
> 按模块分组（`loadscope`）在本框架上**恰好**可行，因为依赖都收敛在单文件内；
> 但这是巧合，依赖一旦跨文件就崩。
> 所以我不去赌这个运气，直接把并发默认关掉，把它当成已知的架构约束。

**面试时千万别说"任何靠全局变量传数据的框架都不可能并发"**——
面试官只要问一句"你试过 `--dist=loadscope` 吗"，这套说法就塌了。
反过来说，**能主动讲出"默认调度下是时好时坏、我用 `--maxschedchunk=1` 稳定复现了失败"**，
那是非常强的加分项：它证明你不只是敲了条命令，而是真的搞清楚了调度模型。

### 要支持并发，得改数据传递方式

| 方案 | 做法 | 代价 |
|---|---|---|
| fixture 传值 | 上游用例返回数据，下游通过 fixture 依赖拿到 | 用例之间耦合变强 |
| 外部存储 | 变量写到文件 / Redis，各进程读同一份 | 引入外部依赖，要处理并发读写 |
| **用例自包含** | 每条用例自己造数据，不依赖上游 | 最彻底，代价是重复请求 |

成熟框架通常用**第三条打底 + 第一条补漏**：尽量让用例自包含；实在需要跨模块的组合场景（比如"建用户 → 下单 → 支付"），就写成**同一条用例**，而不是拆成两条靠变量池串起来。

**`testcases/test_api_style.py::test_full_business_flow` 就是这个做法** —— 把整条链路写在一个函数里，从头到尾自己造数据、自己清理（`finally` 里删用户）。所以它天生是并发安全的。你可以把两个文件对着看一次，这一对比比读十页文档管用。

### 顺带：顺序依赖的危害不只是 `-n`

变量池的顺序依赖还会让下面这些**日常操作**全部踩坑，而它们比并发常用得多：

| 操作 | 会发生什么 |
|---|---|
| 单条执行 `pytest "testcases/test_order.py::test_order[支付订单]"` | 直接 `KeyError: 变量 ${order_id} 不在变量池中` |
| `-k` 筛选 | 前置的生产方用例可能被过滤掉 |
| `pytest --lf`（只跑上次失败的） | 依赖的生产方不在失败集合里 |
| 失败重试 `--reruns 2` | 重试的就是失败的那条，前置照样没有 |
| 随机化顺序插件 | 顺序一乱全崩 |

⚠️ **尤其注意**：`requirements.txt` 里装了 `pytest-rerunfailures`，但**这个框架恰恰不能安全重试**——
重试一条"支付订单"用例意味着**重复支付**。而这条限制在别处没有任何提醒。

> 结论：变量池让 YAML 写起来很爽，代价是**用例不再独立**。
> 这是本框架最值得主动讲出来的设计取舍，见 Q4 / Q7。

> **面试怎么答这题**（答好了很加分）：
> "我的框架用全局变量池解决接口依赖，好处是数据驱动的用例写起来简单，`${}` 占位就行。
> 但代价是用例不再独立：默认的 xdist 多进程调度下不行（进程间内存不共享）；
> 单条执行、`-k` 筛选、`--lf`、失败重试也都会踩到'前置没跑'。
> 所以我默认把并发关掉，检测到 `-n` 会**降级成串行**并给出显式提示——
> 注意这里有个坑：**退出码仍然是 0**，所以 CI 上会'绿着但其实没并发'，
> 我在 CI 里会额外加 `--strict-parallel` 让它直接失败。
> 要真支持并发，得把变量池换成外部存储（文件 / Redis），或者把用例改造成完全不依赖上游。"

# 七、【面试考点】框架设计（最重要）

**Q1：你的框架是怎么分层的？为什么这么分？**

> 分五层：**配置层、公共工具层、请求封装层、业务 API 层、用例数据层**。
> 原则是"改一个东西只动一个地方"：
> 换环境只改 config.yaml，加超时只改 request_util，加用例只改 YAML 不用写代码。
> 其中**请求封装层是心脏**——变量替换、默认超时、日志、异常处理、传输层重试
> 全部收敛在这一层，业务层只关心接口路径和参数。
> 所以我要加一个"所有请求都带签名"的需求，只改这一个文件就够了。

**Q2：用例数据怎么组织的？**

> YAML 文件，一个模块一个文件。每条用例包含 name / request / extract / validate 四部分。
> 用 pytest 的 parametrize 把 YAML 读进来生成用例。
> 好处是加用例不用写代码，业务测试的同事也能维护；坏处是复杂逻辑（循环、条件判断）不好表达，
> 这种场景我就写 Python 用例，两种方式是共存的。

**Q3：接口依赖怎么解决？**

> 三层机制：① 用例里用 `${变量名}` 占位；
> ② 上游用例通过 `extract` 字段用 JSONPath 提取响应字段存进全局字典；
> ③ 发请求前统一做替换。
> 这里有个坑：整串是占位符时要保留原类型，否则 int 的 userId 变成字符串 "5"，服务端匹配不上。

**Q4：怎么保证用例之间不互相影响？**

> ① 每条用例自己准备数据（用 fixture 造临时数据，用完在 teardown 删掉）
> ② 公共数据（token）用 session 级 fixture，只读不写
> ③ 尽量不依赖执行顺序。
>
> 但我要诚实说：本框架目前**还用全局变量池在用例之间传接口依赖**，所以用例并不独立。
> 具体表现是：单条执行、`-k` 筛选、`--lf`、失败重试都会因为"前置没跑"而 KeyError；
> 传 `-n` 时框架会把它忽略、**降级成串行执行并给出显式提示**。
> 要注意这里有个坑：**降级后退出码仍然是 0**，所以 CI 上会"绿着但其实没并发"，
> 我在 CI 里会加 `--strict-parallel` 让它直接失败。
> 要真正解决，得先把依赖数据挪到外部存储，或者改成用例自包含。

**Q5：你的框架有没有接 CI？**

> 用 Jenkins，配 Git webhook 或者定时任务，拉代码 → 装依赖 → 跑 pytest → 出报告 → 失败发钉钉。
> 提交代码时只跑冒烟标记（`-m smoke`），全量放晚上跑。
> （Day 5 详细讲）

**Q6：遇到过什么技术难点？**

挑一个真实的说，比如：
> 接口依赖的类型问题——替换后数字变字符串导致服务端匹配失败，排查了很久，
> 最后在替换函数里区分"整串占位符"和"部分占位符"才解决。
> 或者：用例之间脏数据互相干扰，后来加了 fixture teardown 自动清理 + 每条用例用独立数据。

**诚实提醒**：讲难点时不要编。没遇到过就说"目前框架比较简单，主要在解决 XX 问题"，
然后说出你的判断。编造的细节一追问就露。

**Q7：你的框架还有什么不足？**（这题几乎是必问，答不上来减分）

诚实说，然后说改进方向：
> ① **最要紧的是并发上不去**：框架用全局变量池传接口依赖，而 xdist 是多进程、
>    内存不共享，所以现在传 `-n` 会被框架忽略、降级成串行，用例多的时候跑得慢。
>    更麻烦的是**降级后退出码是 0**，CI 上会是"绿着但没并发"，我现在靠加
>    `--strict-parallel` 让它在 CI 里直接失败来兜住。
>    要真支持并发，得把变量池换成外部存储，或者把用例改造成自包含。
> ② 没有做数据库校验，复杂业务的落库验证还得手工查；
> ③ 报告用 pytest-html，没有 Allure 的趋势分析和历史对比；
> ④ 没有接 CI，仓库里只有 Jenkinsfile 的示例写法，没真跑起来过。
>
> **能说出自己的不足，反而说明你真的做过。**
> 尤其第 ① 条，能讲到"退出码是 0、CI 会假绿"这一层，说明你是真跑过，不是背的。

这四条都是**故意写错的**，跑之前先猜猜会报什么：

| 怎么改 | 你应该看到 |
|---|---|
| 把某条用例的 `validate:` 改成 `validates:` | 收集用例时直接报错「出现未知字段」，**不是**一条绿的 passed |
