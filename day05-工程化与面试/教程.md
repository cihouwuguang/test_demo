# 一、Git（必考，且很容易被问倒）

## 1.1 常用命令

```bash
git clone <地址>              # 拉仓库
git status                    # 看当前状态
git add .                     # 加入暂存区
git commit -m "说明"           # 提交
git push                      # 推到远程
git pull                      # 拉最新代码
git branch                    # 看分支
git checkout -b feature/xxx   # 建并切换分支
git merge <分支名>             # 合并
git log --oneline             # 看提交历史
git diff                      # 看改动
git stash                     # 暂存未提交的改动
git reset --hard HEAD^        # 回退上一个版本（谨慎！）
```

**面试常问**：
- `merge` 和 `rebase` 的区别？
- `git reset` 和 `git revert` 的区别？

## 1.2 必考题：merge vs rebase

> **merge**：把两个分支的改动合并，产生一个新的合并提交，保留完整历史。
> **rebase**：把当前分支的提交"接到"目标分支的后面，历史变成一条直线，更干净。
>
> 实际选择：公共分支（master/develop）用 merge，保留真实历史；
> 自己的 feature 分支同步主干时用 rebase，避免产生一堆无意义的合并提交。
> **rebase 不要用在已经推送到远程的公共分支上**，会改写历史，坑队友。

## 1.3 必考题：reset vs revert

> **reset**：把 HEAD 指针往回移，提交历史被抹掉（`--hard` 连工作区改动一起丢）。
> **revert**：新建一个提交，内容是"撤销某次提交"，历史保留，安全。
>
> 已经推送到远程的提交用 revert（不破坏历史），本地没推的可以用 reset。

## 1.4 分支模型（说得出名字就加分）

```
master/main    生产分支，只接受 release 合并
develop        开发主干
feature/xxx    功能分支，从 develop 切，开发完合并回去
release/x.x    发布分支
hotfix/xxx     线上紧急修复，从 master 切
```

**测试在 Git 流程里的位置**：提测后从 develop（或 release）拉代码部署到测试环境，
测试通过合并到 master。自动化用例一般放在 develop 上跟着开发一起维护。

## 1.5 .gitignore

自动化项目必须忽略的东西：

```
.venv/
__pycache__/
*.pyc
.pytest_cache/
reports/
logs/
allure-results/
```

**为什么要忽略**：报告和日志是运行产物，提交上去会造成无意义的冲突。

# 二、Jenkins（CI/CD）

## 2.1 为什么需要 CI

没有 CI 时：用例写在本地，想起来才跑一次，跑完还得手动看结果。
有了 CI：代码一提交自动跑，失败了钉钉/邮件通知，**测试变成"流水线的一部分"**。

## 2.2 Jenkinsfile 示例

放在项目根目录，Jenkins 读它执行：

```groovy
pipeline {
    agent any

    triggers {
        // 每天晚上 10 点跑全量
        cron('0 22 * * *')
    }

    stages {
        stage('拉代码') {
            steps {
                git branch: 'develop', url: 'https://xxx/auto-test.git'
            }
        }

        stage('装依赖') {
            steps {
                bat 'python -m venv .venv'
                bat '.venv\\Scripts\\pip install -r requirements.txt'
            }
        }

        stage('跑测试') {
            steps {
                // run.py 在 day04 的 framework 目录下，路径要写全
                bat '.venv\\Scripts\\python day04-搭建框架\\framework\\run.py --env=test'
            }
        }

        stage('出报告') {
            steps {
                publishHTML(target: [
                    // 报告目录同样要带上完整路径
                    reportDir: 'day04-搭建框架\\framework\\reports',
                    reportFiles: 'report.html',
                    reportName: '自动化测试报告'
                ])
            }
        }
    }

    post {
        failure {
            // 失败发通知（钉钉/邮件，用插件配）
            echo '用例失败了，发通知'
        }
    }
}
```

## 2.3 面试怎么答 CI 相关的问题

**Q：你们自动化怎么跑的？**

> 用 Jenkins。开发提交代码触发 webhook，或者配定时任务。
> Jenkins 拉代码 → 建虚拟环境装依赖 → 执行 `pytest` → 生成报告 → 归档并发送通知。
> 提交代码时只跑冒烟标记（`-m smoke`），全量回归放晚上跑。

**Q：失败了怎么处理？**

> Jenkins 会发钉钉/邮件通知到群里，带上失败用例名和报告链接。
> 收到后先判断：是用例问题（数据脏了、接口改了）还是真的 bug。
> 真的 bug 就提单给开发，用例问题就修用例。

**加分**：提一句"失败重试只用于环境抖动，重试通过的用例我会单独统计，连续出现就说明用例设计有问题"。

# 三、Allure 报告

pytest-html 够用但不漂亮。Allure 是现在的主流，能出趋势图、分类、历史对比。

```bash
pip install allure-pytest

pytest --alluredir=./allure-results          # 生成原始数据
allure serve ./allure-results                # 启动本地服务看报告
```

需要装 Allure 命令行工具（依赖 Java）。

代码里加注解让报告更详细：

```python
import allure

@allure.feature("用户模块")
@allure.story("登录")
@allure.title("登录成功")
def test_login():
    with allure.step("调用登录接口"):
        ...
    with allure.step("校验返回的 code"):
        ...
```

**面试说辞**：
> 报告用 Allure，按 feature/story 分级，每个用例有步骤描述，
> 失败时能直接看到请求和响应。还支持历史趋势，能看出通过率的变化。

# 四、工程习惯（面试官会观察）

| 习惯 | 为什么重要 |
|---|---|
| 每个函数加 docstring | 别人（和三个月后的你）能看懂 |
| 变量名有意义 | `resp` 比 `r` 好，`case_name` 比 `cn` 好 |
| 断言都带失败信息 | 排查效率差几倍 |
| 参数不写死 | 配置化，换环境不用改代码 |
| 提交前自己跑一遍 | 别把跑不通的代码推上去 |
| 用例能重复跑 | 跑第二次不能因为脏数据失败 |

**最后一条最容易被忽略，也最能暴露水平。**

# 五、面试冲刺：怎么讲项目

详细的逐字稿在 `项目介绍话术.md`，追问预案在 `追问清单与答法.md`。

这里只说三个原则：

## 原则一：用"问题 → 方案 → 结果"的结构

不要一上来就说"我用了 pytest、requests、YAML"。
**先说问题**（痛点），**再说你怎么解决的**，最后说**效果**。

> ❌ "我的框架用了 pytest 和 requests，做了分层和数据驱动。"
>
> ✅ "之前接口回归全靠手工点，一次要半小时还容易漏。
>     我用 Python 写了个自动化框架，用例数据放在 YAML 里，
>     现在一条命令跑完 100 条用例只要 2 分钟，提交代码时自动触发。"

第二种说法有场景、有数字、有价值。

## 原则二：准备好"为什么"

每个设计决策都要能说出理由：

- 为什么分层？→ 改一个东西只动一个地方
- 为什么用 YAML？→ 加用例不用写代码，业务同事也能维护
- 为什么用 Session？→ 复用连接、自动带 cookie、统一设 header
- 为什么用 session 级 fixture？→ 避免每条用例重复登录

**说不出"为什么" = 说明是抄的。**

## 原则三：诚实标注边界

| 情况 | 怎么说 |
|---|---|
| 跟着教程做的 | "我参考开源项目搭了一套，按自己的理解改了 XX 部分" |
| 只有练习项目 | "这是我自学的练手项目，没在公司落地" |
| 只做过一个模块 | "我负责的是 XX 模块，其他部分是同事做的" |

**不要**：把自学项目说成公司项目、把别人的工作说成自己的。
技术面试的追问很深，编造的细节一定会被问穿，而且背调风险大。

# 六、最后的自检清单

面试前一晚，对着这个过一遍：

**能手写**
- [ ] 一个统计函数耗时的装饰器
- [ ] 一个 yield 做前后置的 fixture
- [ ] 一个带继承的类（父类封装、子类业务）

**能说清**
- [ ] `params` / `data` / `json` 的区别
- [ ] Session 的三个好处
- [ ] fixture 的 5 种 scope
- [ ] 你的框架分几层，每层干什么
- [ ] 接口依赖怎么解决的
- [ ] 用例之间怎么防干扰

**能讲出故事**
- [ ] 1 分钟介绍你的项目
- [ ] 一个你印象最深的技术难点
- [ ] 你的框架还有什么不足，打算怎么改

**准备一个反问**
- [ ] 团队现在自动化做到什么程度？
- [ ] 进去之后主要负责哪块？
- [ ] 用例维护是谁来做？
