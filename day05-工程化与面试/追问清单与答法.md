# 一、Python 基础

**1. 手写一个装饰器，统计函数运行时间**
```python
import time, functools

def timer(func):
    @functools.wraps(func)
    def inner(*args, **kwargs):
        start = time.time()
        result = func(*args, **kwargs)
        print(f"[{func.__name__}] 耗时 {time.time() - start:.3f}s")
        return result
    return inner
```
要点：三层别漏——`*args/**kwargs`、`return result`、`functools.wraps`。

**2. yield 和 return 的区别？**
> return 返回后函数结束，下次从头执行；yield 返回后在原地暂停，下次从暂停处继续。
> 含 yield 的函数调用时返回生成器，函数体不立即执行。
> 好处是惰性求值、省内存。

**3. fixture 为什么用 yield 不用 return？**
> 需要前后置：yield 前是 setup，yield 后是 teardown。
> 用 return 函数直接结束，清理代码执行不到。
> 而且 pytest 保证用例失败时 teardown 也执行。

**4. 深拷贝和浅拷贝的区别？**
> 浅拷贝只复制最外层，内部的子对象还是共享同一份（`copy.copy`、列表切片、`dict()`）。
> 深拷贝递归复制所有层级，完全独立（`copy.deepcopy`）。
> 坑：嵌套列表用浅拷贝，改内层两个都变。

**5. `*args` 和 `**kwargs` 是什么？**
> `*args` 接收任意多个位置参数，打包成元组；`**kwargs` 接收关键字参数，打包成字典。
> 装饰器里必须用它，因为不知道被装饰函数有几个参数。
> 调用时 `func(*args, **kwargs)` 是解包。

**6. 类属性和实例属性的区别？**
> 类属性在类里、方法外，所有实例共享，改一处全局生效；
> 实例属性在 `__init__` 里用 `self.xxx`，每个实例独立。
> 坑：可变类型（list/dict）当类属性时，一个实例 `append` 会影响所有实例。

**7. `__init__` 和 `__new__` 的区别？**
> `__new__` 创建对象（分配内存），参数是 cls，先执行；
> `__init__` 初始化对象（赋属性），参数是 self，后执行。
> 一般只写 `__init__`，`__new__` 用于单例等场景。

**8. 什么是 GIL？**
> 全局解释器锁，CPython 里同一时刻只有一个线程能执行 Python 字节码。
> 所以 CPU 密集型任务用多线程不能真并行，要用多进程；
> IO 密集型（网络请求）多线程仍然有效，因为等待时会释放锁。

# 二、pytest

**9. fixture 的 scope 有哪几种？**
> function（默认，每用例）、class（每类）、module（每文件）、package（每包）、session（全程）。
> 登录 token 和数据库连接用 session，用例专属数据用 function。

**10. conftest.py 是干嘛的？**
> 放公共 fixture 的特殊文件，对同级及子目录所有用例生效，不用 import。
> 可以有多个，子目录优先级更高。

**11. pytest 和 unittest 的区别？**
> ① pytest 用例是普通函数不用继承类
> ② 直接 assert，失败还显示变量值（断言重写）
> ③ fixture 比 setUp/tearDown 灵活，5 种作用域 + 依赖注入
> ④ 参数化内置，unittest 要靠 ddt
> ⑤ 插件生态丰富

**12. 怎么只跑一部分用例？**
> `-m 标记`、`-k 名字关键字`、`路径::用例名` 精确指定。

**13. skip 和 xfail 的区别？**
> skip 是完全不执行；xfail 是执行了，但预期它失败，失败不算失败。
> xfail 用于标记已知 bug，比注释掉用例好——问题还在视野里。

**14. 用例不稳定（偶现失败）怎么办？**
> ① 先排查用例本身：数据没清理、接口依赖没做、有并发冲突
> ② 确认是环境抖动再加重试（`--reruns 2`）
> ③ 重试会掩盖问题，重试通过的用例要单独统计、定期审查

**15. 用例多了跑得慢怎么办？**
> `pytest -n auto` 并发（xdist）。
> 前提是用例无依赖、不共享可变数据。
> 另外分层：提交跑冒烟，全量放晚上。

⚠️ **只说到这里会被追着问。备好下一层**：
> xdist 的 `-n` 是开进程，不是开线程，每个 worker 内存独立。
> 所以如果用例之间靠全局变量传数据，并发就会取不到值。
> 我自己的框架就卡在这——用变量池传接口依赖，所以现在跑不了 `-n`，
> 得先把依赖数据挪到外部存储，或者把跨模块链路写成一条自包含用例。
>
> **主动说出自己框架的这条限制，比等着被问出来强得多。** 它同时证明了
> 你真的跑过并发、也理解 xdist 的进程模型，而不是只会敲一个 `-n auto`。

# 三、requests 与接口测试

**16. Session 有什么用？**
> ① 自动维持 cookie ② 复用 TCP 连接（连接池，更快）③ 统一设默认 headers/timeout。

**17. params / data / json 的区别？**
> params 拼 URL 查询串（GET 用）；data 表单编码放请求体；
> json 是 JSON 编码，且自动加 `Content-Type: application/json`。
> 用错会导致服务端解析不到参数。

**18. 接口依赖怎么解决？**
> JSONPath 从上游响应提取字段 → 存全局字典 → 下游用例用 `${}` 占位 → 发请求前替换。
> 坑：整串占位符要保留原类型，否则 int 变 str 匹配不上。

**19. 为什么要查数据库？**
> 接口返回成功不代表数据真的落库——可能事务回滚、异步失败、只改了缓存。
> 金融类业务必须做库表校验。

**20. 接口返回 200 但业务失败，算 bug 吗？**
> 不算。很多系统 HTTP 状态码只表示"请求被处理了"，业务结果看响应体的 code。
> 所以断言要两层：HTTP 状态码 + 业务 code。

**21. GET 和 POST 的区别？**
> 用途（获取 vs 提交）、参数位置（URL vs 请求体）、长度限制、
> 安全性（GET 参数在 URL 上会留痕）。
> 加分：GET 规范上应该幂等且无副作用，POST 允许改变状态。

**22. 401 和 403 的区别？**
> 401 未认证（没登录/token 无效），403 未授权（身份知道但权限不够）。

**23. Cookie / Session / Token 的区别？**
> Cookie 在客户端，每次自动带；Session 在服务端，靠 cookie 里的 sessionId 找；
> Token 在客户端，服务端不存，适合分布式和多端。
> 加分：JWT 把信息放 token 里，服务端只验签，缺点是难以主动失效。

**24. 金额字段怎么处理？**
> 数据库用 DECIMAL，代码用 Decimal 类，或者以分为单位存整数。绝不用 float。
> 比较用差值（`abs(a-b) < 0.01`）而不是 `==`。

# 四、框架设计（最重要）

**25. 你的框架怎么分层的？为什么？**
> 五层：配置、公共工具、请求封装、业务 API、用例数据。
> 原则：改一个东西只动一个地方。
> 换环境改 config，加超时改请求封装，加用例改 YAML 不用写代码。

**26. 用例数据怎么组织？**
> YAML，一个模块一个文件，每条用例含 name/request/extract/validate。
> 用 parametrize 读进来生成用例。
> 加用例不用写代码，业务同事也能维护；
> 复杂逻辑（循环、条件）不好表达，那种场景写 Python，两种共存。

**27. 怎么保证用例之间不互相影响？**
> ① 每条用例自己准备数据（fixture 造，teardown 删）
> ② 公共数据（token）用 session 级，只读不写
> ③ 用例尽量不依赖执行顺序——将来要并发，有顺序依赖就会乱

**28. 你的框架有什么不足？**（必问，答不出减分）
> 挑 2-3 个真实存在的说：
> ① **并发上不去（最实在的一条）**：框架用全局变量池传接口依赖，
>    而 xdist 的 `-n` 是多进程、内存不共享，现在跑 `-n` 会直接失败。
>    要支持并发得把变量池换成外部存储，或者把用例改造成自包含。
> ② 没有做数据库校验，复杂业务的落库验证还得手工查；
> ③ 报告用 pytest-html，没有 Allure 的趋势分析和历史对比。
>
> **能说出不足反而说明真做过。** 尤其第 ① 条，能讲到"进程模型"这一层，
> 说明你是真踩过，不是背的。

**29. 遇到过什么技术难点？**
> 说真话。比如"接口依赖替换后类型变了，排查了很久才发现是字符串强转的问题"。
> 编造的细节一追问就穿。

**30. 日志为什么重要？**
> 自动化的价值是无人值守跑完还能定位问题。
> 用例半夜挂了，早上只能看日志。没日志的框架等于白跑。

**31. 怎么切换测试环境？**
> 配置抽到 YAML，按环境分节（test/prod），
> 通过 default_env 或命令行 `--env=prod` 切换。

**32. 你的用例覆盖率怎么样？**
> 不要吹数字。说"覆盖了 XX 模块的核心场景，
> 主要是正向流程 + 参数校验 + 异常场景 + 安全（无 token）"。

# 五、项目与协作

**33. 你和开发意见不一致怎么办？**
> 先确认复现步骤和预期结果，拿接口文档或需求对着看；
> 还是不一致就拉产品/需求方确认。
> 重点是**用事实说话**（日志、抓包、文档），不是靠感觉争。

**34. 发现一个 bug，开发说"不是 bug"？**
> ① 确认是不是环境/数据问题
> ② 找需求文档或接口文档作为依据
> ③ 说明影响（用户会怎样）
> ④ 达不成一致就升级，记录到缺陷系统留痕

**35. 你怎么判断是前端还是后端的问题？**
> 抓包看请求：
> 请求没发出去或参数错了 → 前端；
> 请求正常但响应数据不对 → 后端；
> 响应对但页面显示错 → 前端。
> 再查服务端日志确认。

**36. 你怎么做接口测试用例设计？**
> 分四层：
> ① 正向：正常参数，校验返回和业务状态
> ② 参数校验：必填、类型、长度、边界、特殊字符
> ③ 异常场景：不存在的 id、无权限、重复提交（幂等）
> ④ 安全：不带 token、token 过期、签名错误

**37. 你觉得自动化能替代手工测试吗？**
> 不能。自动化擅长回归和重复执行，
> 探索性测试、易用性、视觉、新功能的第一次验证还是要人。
> 自动化的价值是把人从重复劳动里解放出来，去做更需要判断力的事。

**38. 什么项目不适合做自动化？**
> 需求频繁变动的、一次性验证的、强依赖视觉/交互的、UI 极不稳定的。
> 接口自动化比 UI 自动化 ROI 高，因为接口稳定、执行快。

# 六、开放题（考思维方式）

**39. 给你一个新项目，你怎么开展自动化？**
> ① 先手工跑一遍熟悉业务和接口
> ② 选核心、稳定、高频的模块优先做（比如下单、支付）
> ③ 搭框架：配置、封装、数据驱动
> ④ 先跑通一条链路，再批量铺量
> ⑤ 接 CI，配冒烟和全量
> ⑥ 持续维护：失败用例及时修，不维护的框架很快会烂掉

**40. 你怎么衡量自动化做得好不好？**
> 不要只说覆盖率。说这些更有说服力：
> ① 稳定性：误报率（不是真的 bug 却失败）高不高
> ② 有效性：有没有真的发现过 bug
> ③ 维护成本：接口变了要改多少地方
> ④ 执行时间：能不能在 CI 里及时反馈

**41. 自动化用例一直没人维护，你怎么办？**
> 先分析原因：跑不起来？结果没人信？还是没人会用？
> 我会先把失败的用例修到全绿，再接 CI 让结果可见，
> 然后推动"提交代码必须跑冒烟"变成流程的一部分。
> 关键是让自动化**产生可见的价值**，不然推不动。

**42. 你为什么想做测试开发/自动化？**
> 诚实说。比如"做功能测试时发现重复回归很枯燥，
> 而且手工容易漏，就想用代码解决，后来发现设计框架本身也挺有意思"。

# 七、三个"答不上来"的救场话术

| 情况 | 怎么说 |
|---|---|
| 完全没听过 | "这个我没接触过，能简单说一下吗？"（然后听完说理解） |
| 听过但说不清 | "这个概念我用过，但要我说准确定义可能说不好，我的理解是……" |
| 被问穿了 | "您说的这点我确实没考虑到，我回去查一下" |

**不要硬编。** 承认不知道然后说出自己的理解，比编一个错的强得多。
面试官考的是你的思维方式，不是百科全书。
