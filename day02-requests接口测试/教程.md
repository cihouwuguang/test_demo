## 为什么不用 Postman 而要用代码

你有 CloudTest 的经验，那 Postman 类的工具你很熟。那为什么还要写代码？

# 一、HTTP 快速回炉

你有接口测试底子，这里只挑容易混淆的点。

## 1.1 请求长什么样

```
POST /api/login HTTP/1.1              ← 请求行：方法 + 路径 + 协议
Host: 127.0.0.1:5000                  ← 请求头开始
Content-Type: application/json
token: abc123
                                      ← 空行，下面是请求体
{"username":"admin","password":"123456"}
```

## 1.2 状态码（面试必考，别只背 200/404）

| 码 | 含义 | 自动化里怎么处理 |
|---|---|---|
| 200 | 成功 | 继续校验业务 code |
| 201 | 创建成功 | 同上 |
| 204 | 成功但无响应体 | 解析 JSON 会报错！要特殊处理 |
| 301/302 | 重定向 | requests 默认自动跟随 |
| 400 | 请求参数错 | **客户端问题**，检查用例数据 |
| 401 | 未认证 | token 没带或过期 |
| 403 | 无权限 | token 有效但权限不够 |
| 404 | 路径不存在 | 检查 URL 拼错没有 |
| 405 | 方法不允许 | GET/POST 用错了 |
| 500 | 服务器内部错误 | **服务端 bug**，提单 |
| 502/504 | 网关错误/超时 | 服务挂了或太慢 |

**面试常考**：`401` 和 `403` 的区别？
> 401 是"你谁啊"（没登录/token 无效），403 是"你是谁我知道，但你没权限"。

**另一个常考**：HTTP 状态码返回 200，但业务失败了（比如 `{"code": 1003, "msg": "密码错误"}`），这算 bug 吗？
> 不算。很多系统 HTTP 状态码只表示"请求到达并被处理了"，业务结果要看响应体里的 `code`。
> 所以断言要**两层都做**：HTTP 状态码 + 业务 code。

## 1.3 GET 和 POST 的区别（面试必考）

标准答案分四层：

1. **用途**：GET 是获取，POST 是提交
2. **参数位置**：GET 参数在 URL 上（query string），POST 在请求体里
3. **长度**：GET 受 URL 长度限制（浏览器一般 2KB~8KB），POST 没有
4. **安全性**：GET 参数明文在 URL 上、会被浏览器记录，所以**不能传密码**；但两者都不加密，**都不是真安全**，要安全得用 HTTPS

**加分点**（说出这个说明你真的懂）：
> GET 在规范上是"幂等且安全"的，不应该改变服务器状态；POST 允许有副作用。
> 所以"用 GET 做删除操作"是不规范的设计。

# 二、requests 基础

## 2.1 第一个请求

```python
import requests

resp = requests.get("http://127.0.0.1:5000/api/users")
print(resp.status_code)   # 200
print(resp.text)          # 字符串形式的响应体
```

## 2.2 响应对象有什么

| 属性/方法 | 说明 |
|---|---|
| `resp.status_code` | HTTP 状态码 |
| `resp.text` | 响应体（字符串） |
| `resp.json()` | 响应体转成字典（**响应不是合法 JSON 时会抛异常**） |
| `resp.headers` | 响应头（字典） |
| `resp.cookies` | 响应的 cookie |
| `resp.elapsed` | 耗时 |
| `resp.encoding` | 编码，中文乱码时手动设 `resp.encoding = "utf-8"` |

```python
data = resp.json()
print(data["code"])
```

> 坑：`resp.json()` 在响应是 HTML（比如 502 页面）时会抛 `JSONDecodeError`。
> 框架里要 try 一下或者先判断 `Content-Type`。

## 2.3 三个传参参数的区别（**必考，最容易搞混**）

```python
# 1. params —— 拼到 URL 后面，?key=value
requests.get(url, params={"page": 1, "size": 10})
# 实际请求：GET /api/users?page=1&size=10

# 2. data —— 表单格式，Content-Type: application/x-www-form-urlencoded
requests.post(url, data={"username": "admin", "pwd": "123"})
# 实际请求体：username=admin&pwd=123

# 3. json —— JSON 格式，Content-Type: application/json
requests.post(url, json={"username": "admin", "pwd": "123"})
# 实际请求体：{"username": "admin", "pwd": "123"}
```

**怎么记**：
- GET 一般配 `params`
- POST 配 `data` 还是 `json`，**看接口文档要求什么 Content-Type**
- 现在绝大多数接口（尤其 JSON API）用 `json=`

**判断错了会怎样**：接口要求 JSON，你传了 `data=`，服务端解析不到 body，返回 400 或者报参数缺失。这是新手最常见的"我明明传了参数啊"。

## 2.4 请求头

```python
headers = {
    "Content-Type": "application/json",
    "token": "mock_token_abc123",
}
requests.get(url, headers=headers)
```

> 注意：用 `json=` 参数时 requests 会**自动加** `Content-Type: application/json`，
> 手动再写一遍也没关系，但不要写成 `application/x-www-form-urlencoded`，会冲突。

## 2.5 timeout（很多人忘，面试会问，而且**极易答错**）

```python
requests.get(url, timeout=5)
```

不加 timeout 的后果：服务端不响应时，**程序会一直卡着**，整个测试挂死。

### ⚠️ 第一条必须纠正的常见错误说法

> ❌ 「`timeout=5` 表示连接 + 读取**总共**最多等 5 秒」

**这是错的。** requests 的单值 timeout 会同时赋给 **connect** 和 **read** 两个独立超时：

```python
# requests 内部（HTTPAdapter.send）等价于：
TimeoutSauce(connect=timeout, read=timeout)
```

而 **read 超时的定义是「两次收到字节之间的最大间隔」**，不是「整个响应读完的总时长」。

**实测**（`code/05_sign_and_exception.py` 第 4 节可以直接跑）：造一个每 1 秒吐一块、
总共吐 8 秒的「慢速滴流」接口，用 `timeout=5` 去调：

```
结果：HTTP 200，耗时 8.0 秒     ← 超过 5 秒了，却没有超时！
```

因为「每 1 秒收到一块」< 5 秒，read 超时永远不会触发。

### 正确的理解

| 写法 | 真实含义 |
|---|---|
| `timeout=5` | `timeout=(5, 5)`：连接最多 5 秒；**两次收到字节之间**最多等 5 秒 |
| `timeout=(3, 10)` | 连接最多 3 秒；两次收到字节之间最多等 10 秒 |
| 想要「整个请求最多 N 秒」 | **requests 没有这个能力** |

**那要控总时长怎么办？**（这是加分点）

1. **用例层自己计时**：`t0 = time.time()` … 断言 `elapsed < N`；
2. **换 httpx**：它支持 `httpx.Timeout(10, connect=3)` 这种带总时长语义的写法。

> **面试怎么说**：
> "requests 的 timeout 是 connect 和 read 两个独立超时，read 指的是两次收到数据的**间隔**，
> 所以它没有请求级的总时长超时。如果业务要求"这个接口必须 3 秒内返回"，
> 我会在用例层自己计时断言，或者用 httpx 的 `Timeout(total=...)`。"
>
> 能说到这个层次，说明你真跑过；说成"总共 5 秒"，只能说明只背了 API。

# 三、Session（重点）

## 3.1 为什么需要 Session

HTTP 是**无状态**的——服务器记不住你上一次请求是谁。
所以登录后要带上凭证（cookie 或 token）证明身份。

`requests.Session()` 帮你做三件事：

1. **自动保存和携带 cookie**（登录后访问其他接口不用手动带）
2. **复用 TCP 连接**（性能更好，尤其跑几百条用例时）
3. **统一设置默认的 headers 和 cookie**

> ⚠️ **注意第 3 条里没有 timeout。** Session **不能**统一设置 timeout——
> `s = requests.Session(); s.timeout = 1` 这种写法**完全无效**，
> requests 不会去读 Session 上的 `timeout` 属性，请求照样按默认（无限）等下去。
> 实测：服务端卡 3 秒时，`requests.get(url, timeout=1)` 会抛 Timeout，
> 而设了 `s.timeout = 1` 的 `s.get(url)` 会正常返回 200。
>
> **这是「你怎么统一管理超时」这个标准追问的落点**，正确做法是继承 Session 重写 `request`：
>
> ```python
> class TimeoutSession(requests.Session):
>     def __init__(self, timeout=10):
>         super().__init__()
>         self._timeout = timeout
>
>     def request(self, method, url, **kwargs):
>         # setdefault：调用方显式传了 timeout 就用他的，没传用默认值
>         kwargs.setdefault("timeout", self._timeout)
>         return super().request(method, url, **kwargs)
> ```
>
> 本项目 Day4 的 `common/request_util.py` 就是这么做的
> （`kwargs.setdefault("timeout", self.config.timeout)`），学到这里时回头对一眼。

## 3.2 用法

```python
import requests

s = requests.Session()

# 统一设置，后续所有请求都带上
s.headers.update({"Content-Type": "application/json"})

# 登录，服务器返回的 cookie 会自动存到 s 里
s.post("http://127.0.0.1:5000/api/login", json={"username": "admin", "password": "123456"})

# 后续请求自动带 cookie，不用手动传
resp = s.get("http://127.0.0.1:5000/api/users")
```

对比一下不用 Session：

```python
# 不用 Session：每次都要手动带
resp1 = requests.post(login_url, json=...)
cookie = resp1.cookies
resp2 = requests.get(users_url, cookies=cookie)    # 手动传
resp3 = requests.get(order_url, cookies=cookie)    # 每次都要传
```

## 3.3 token 鉴权怎么做

现在很多接口不用 cookie，而是**登录返回 token，后续请求放 header 里**：

```python
s = requests.Session()

# 1. 登录拿 token
resp = s.post(login_url, json={"username": "admin", "password": "123456"})
token = resp.json()["data"]["token"]

# 2. 把 token 放到 Session 的默认请求头里
s.headers.update({"token": token})

# 3. 后续所有请求自动带上
s.get("http://127.0.0.1:5000/api/user/1")
```

**这是自动化框架的标准做法**：登录一次，token 全局复用。

> 术语解释：
> - **Cookie**：服务器种在浏览器/客户端的小段数据，每次请求自动带上
> - **Session**：服务器端保存的用户状态，靠 cookie 里的 sessionId 对应
> - **Token**：登录成功后服务器发的"令牌"，客户端自己存，请求时带上
> - **JWT**：一种 token 的**格式**（RFC 7519）。见下面的重要澄清 👇

### ⚠️ 必纠正：JWT / JWS / JWE 不是一回事

这三个词经常被混着说，而在金融、终端、安全方向的面试里，说错会被当场标记。

| 缩写 | 全称 | 干什么 | RFC |
|---|---|---|---|
| **JWT** | JSON Web Token | 一种 **token 格式**，定义"长什么样" | 7519 |
| **JWS** | JSON Web **Signature** | **签名**，防篡改。内容是 base64url，**可读** | 7515 |
| **JWE** | JSON Web **Encryption** | **加密**，防窃听。内容不可读 | 7516 |

**关键结论**：

- **JWT 默认是 JWS**，即**只签名、不加密**。payload 就是 base64url，
  随便找个在线工具粘进去就能看到明文。
- 所以 **JWT 里绝对不能放敏感信息**（密码、身份证、银行卡）。
  它靠**签名**防篡改，靠 **HTTPS** 防窃听。
- 要真加密，得用 **JWE**（可单独用，也可以"先签名再加密"或"加密后再签名"组合用）。
- 「**RSA 私钥签名、对方公钥/服务端验签**」描述的是 **JWS（RS256）**，**不是 JWE**。

> **面试怎么说**：
> "token 用 JWT 格式的话，默认是 JWS，只签名不加密，payload 是可读的，
> 所以里面只放 userId 这类非敏感信息，防篡改靠签名、防窃听靠 HTTPS。
> 如果确实要传敏感数据，得用 JWE 做加密，或者字段级加密。"
>
> 别把"签名"说成"加密"。这两个词在安全岗/金融岗的面试里是硬性区分。

## 3.4 Cookie / Session / Token 的区别（面试必考）

| | 存哪里 | 谁管状态 | 特点 |
|---|---|---|---|
| Cookie | 客户端 | 无 | 每次请求自动带，有大小限制（4KB） |
| Session | 服务端 | 服务端 | 靠 cookie 里的 sessionId 找，占服务器内存 |
| Token | 客户端 | 无 | 服务端不用存，适合分布式/微服务 |

**加分回答**：
> Cookie + Session 是传统 Web 的方案，服务端要存状态，做分布式得解决 session 共享问题。
> Token（尤其 JWT）把状态放客户端，服务端只验签，天然适合微服务和多端（App/小程序没有 cookie 机制）。
> 缺点：Token 一旦发出去，服务端很难主动让它失效（要配合黑名单或短过期时间 + 刷新机制）。

# 四、响应提取与接口依赖

## 4.1 问题：下一个接口要用到上一个接口的返回值

典型场景：创建用户返回 `id`，查询用户要用这个 `id`。

```python
# 创建
resp = s.post(url + "/api/user", json={"username": "newuser", "phone": "13700000000"})
user_id = resp.json()["data"]["id"]        # 一层层取

# 查询
resp2 = s.get(f"{url}/api/user/{user_id}")
```

直接一层层取 `["data"]["id"]` 能用，但：
- 层级深了写着烦
- 字段不存在会 KeyError

## 4.2 用 JSONPath 提取（框架里的标准做法）

> 术语解释：**JSONPath** 是 JSON 版的 XPath，用表达式从 JSON 里取值。

```python
from jsonpath_ng import parse

data = {"code": 0, "data": {"list": [{"id": 1}, {"id": 2}]}}

expr = parse("$.data.list[0].id")
matches = expr.find(data)
print(matches[0].value)      # 1
```

常用语法：

| 表达式 | 含义 |
|---|---|
| `$` | 根节点 |
| `$.code` | 取 code 字段 |
| `$.data.list[0]` | 列表第一个元素 |
| `$.data.list[*].id` | 所有元素的 id |
| `$..id` | 递归找所有 id |

封装一下（Day 4 会用到）：

```python
def extract(resp_json, expr):
    """从响应里按表达式取值，取不到返回 None"""
    matches = parse(expr).find(resp_json)
    return matches[0].value if matches else None
```

## 4.3 变量池：解决接口依赖的通用方案

思路：
1. 上游接口的响应，按规则提取出来，存进一个全局字典
2. 下游用例里用 `${变量名}` 占位
3. 发请求前把 `${}` 替换成真实值

```python
VARS = {}    # 全局变量池

# 提取阶段
VARS["user_id"] = extract(resp.json(), "$.data.id")

# 使用阶段：用例里写
{"userId": "${user_id}"}

# 替换阶段
import re
def replace_vars(data):
    """把字符串里的 ${xxx} 换成变量池里的值"""
    if isinstance(data, str):
        for k, v in VARS.items():
            data = data.replace("${" + k + "}", str(v))
        return data
    if isinstance(data, dict):
        return {k: replace_vars(v) for k, v in data.items()}
    if isinstance(data, list):
        return [replace_vars(i) for i in data]
    return data
```

**这就是数据驱动框架的核心机制**，Day 4 会完整实现。

## 4.4 一个必踩的坑：替换后类型变了

上面的 `replace_vars` 有个隐藏 bug。看这个场景：

```python
VARS["user_id"] = 5                          # 提取出来是 int
body = {"userId": "${user_id}"}
# 如果一律 str() 强转 → {"userId": "5"}      # 变成字符串了！
```

后果：服务端按整数查用户，收到 `"5"` 匹配不上，返回"用户不存在"。
**这种 bug 特别难查，因为肉眼看参数明明是对的。**

正确做法：**整串就是一个占位符时保留原类型，只有占位符是字符串的一部分时才转字符串**。

```python
def replace_vars(data):
    if isinstance(data, str):
        # 整串就是 ${xxx} → 原样返回，保留 int/float 类型
        full = re.fullmatch(r"\$\{(\w+)\}", data)
        if full:
            return VARS[full.group(1)]
        # 只是其中一部分 → 只能转成字符串拼接
        return re.sub(r"\$\{(\w+)\}", lambda m: str(VARS[m.group(1)]), data)
    ...
```

> 这个坑在 `code/03_extract_dependency.py` 里有完整演示，跑一遍看输出。
> **面试时主动讲出这个坑，是很好的加分点**——说明你是真踩过，不是背的。

# 五、数据库校验（区分新手和老手的分水岭）

## 5.1 为什么要查数据库

**只断言接口返回是不够的。**

真实 bug 长这样：
```
接口返回：{"code": 0, "msg": "下单成功"}
数据库：  订单表空空如也
```

原因可能是：接口返回成功，但异步落库失败、或者事务回滚了、或者只改了缓存没改库。

**所以关键业务必须做数据库校验**：调完接口，去库里查一遍，确认数据真的对。

## 5.2 Python 操作数据库

MySQL 用 `pymysql`，这里用 Python 内置的 `sqlite3` 演示（语法几乎一样，不用装东西）。

```python
import sqlite3

conn = sqlite3.connect("test.db")
cursor = conn.cursor()

cursor.execute("SELECT * FROM users WHERE id = ?", (1,))
row = cursor.fetchone()        # 查一条
rows = cursor.fetchall()       # 查所有

cursor.close()
conn.close()
```

**要点**：
- SQL 里的参数用 `?` 占位，不要字符串拼接（防 SQL 注入，也是好习惯）
- MySQL 的 `pymysql` 用 `%s` 占位，写法：`cursor.execute("SELECT * FROM users WHERE id = %s", (1,))`
- 增删改之后要 `conn.commit()`，查询不用

## 5.3 完整例子：下单后校验数据库

```python
# 1. 调接口
resp = s.post(url + "/api/order", json={"userId": 1, "amount": 99.9})
order_id = resp.json()["data"]["orderId"]

# 2. 查库
cursor.execute("SELECT status, amount FROM orders WHERE order_id = ?", (order_id,))
row = cursor.fetchone()

# 3. 断言
assert row is not None, "数据库里没查到订单！"
assert row[0] == "CREATED", f"订单状态不对：{row[0]}"
assert abs(row[1] - 99.9) < 0.01, f"金额不对：{row[1]}"
```

## 5.4 金额为什么不能用 float 比较

```python
0.1 + 0.2 == 0.3        # False！
```

二进制浮点数的精度问题。**金额比较必须这样**：

```python
from decimal import Decimal

Decimal("0.1") + Decimal("0.2") == Decimal("0.3")    # True

# 或者比较差值
abs(a - b) < 0.01
```

**面试考点**：金额字段怎么处理？
> 数据库用 `DECIMAL` 类型（不用 float/double），代码里用 `Decimal`，
> 或者**以分为单位存整数**（99.9 元存 9990 分），从根上避免精度问题。

# 六、异常场景处理

## 6.1 超时

```python
try:
    requests.get(url + "/api/slow", timeout=1)     # mock 的 slow 接口要 3 秒
except requests.exceptions.Timeout:
    print("超时了")
```

## 6.2 服务端报错

```python
try:
    resp = requests.get(url + "/api/error")
    resp.raise_for_status()          # ← 关键：不加这一行，下面的 except 永远进不去
except requests.exceptions.HTTPError as e:
    print(f"服务端返回了错误状态码：{e}")     # 500 Server Error
```

### ⚠️ 一个经典的错误写法（很多教程都写错）

你可能会看到（也可能自己写出）这样的代码：

```python
# ❌ 这段代码的 except 分支永远不会执行
try:
    requests.get(url + "/api/error")
except requests.exceptions.RequestException as e:
    print(f"请求异常：{e}")
```

**为什么永远不执行？** 因为 `/api/error` 返回的是 **HTTP 500 + 一个 HTML 错误页**——
那**是一个正常的响应**。requests 只有在"连不上、超时、协议出错"这类**传输层**问题才抛异常。

> **requests 不会因为 4xx / 5xx 抛异常**，它认为"拿到响应了就算成功"。
> 想让错误状态码变成异常，必须**手动**调 `raise_for_status()`。

这个例子在教一个不存在的现象——所以本节特意把它改成正确写法。
你可以自己验证：把 `raise_for_status()` 那行注释掉，脚本一点反应都没有。

## 6.3 `raise_for_status()`

```python
resp = requests.get(url)
resp.raise_for_status()      # 状态码是 4xx/5xx 时抛 HTTPError
```

> 注意：requests **不会**因为 404/500 自动抛异常，它认为"拿到响应了就算成功"。
> 想让错误状态码变异常，得手动调 `raise_for_status()`。这个坑很多人踩。

## 6.4 签名接口

很多金融/支付接口要求对参数签名防篡改。mock 里提供了一个演示接口：

规则：`sign = md5(SIGN_KEY + 参数按 key 升序拼接 + timestamp)`

```python
import hashlib
import time

body = {"amount": 100, "userId": 1}
timestamp = str(int(time.time()))

raw = "".join(f"{k}{body[k]}" for k in sorted(body.keys()))
sign = hashlib.md5((SIGN_KEY + raw + timestamp).encode()).hexdigest()

requests.post(url + "/api/sign/verify", json=body,
              headers={"sign": sign, "timestamp": timestamp})
```

**你做过金融级的报文签名，这块是加分项**。面试时可以主动提：

> 签名一般三个作用：防篡改（参数被改了签名对不上）、防重放（加时间戳 + nonce，
> 同样的请求不能重复发）、验身份（密钥只有双方知道，能确认是谁发的）。

**注意措辞**：说"签名"，不要说"加密"（见 3.3 的 JWS / JWE 澄清）。
如果要说自己项目里的具体实现，照实说：

> "报文是先做 RSA 私钥签名，对方用公钥验签"——这是 **JWS(RS256)** 语义；
> 如果确实是"把报文体加密后再传"，那才是 JWE。**两个都用了就说都用了**。
> 别为了显得高级把签名说成加密，一追问就穿。

### 一个真实的安全缺陷类型：错误信息回显

本 mock 的验签接口原来犯过一个错——签名不匹配时这样返回：

```python
return fail(4003, f"签名错误，期望 {expect}")     # ❌ 把正确签名告诉了调用方
```

后果是一条完整的绕过链：

```
① 篡改 amount，带着旧签名发送
   → {'code': 4003, 'msg': '签名错误，期望 15dae6cbf456e7191a341c4f35617aaf'}
② 从错误信息里把「期望签名」读出来
③ 用这个签名重发同样的篡改请求
   → {'code': 0, 'data': {'msg': '验签通过'}}      ← 防篡改形同虚设
```

**错误信息回显敏感内容**（期望值、内部路径、SQL、堆栈）是一类真实存在的安全缺陷，
测试是可以发现它的：只要检查"返回的 msg 里有没有泄漏本不该给调用方的信息"。

现在 mock 已改成只回「签名错误」。`code/05_sign_and_exception.py` 的第 3 节加了一条断言，
专门守住这一点——**如果 mock 以后又把期望签名回显出来，那条用例会立刻失败**。
这就是"把安全要求写成可执行的用例"。

# 七、【面试考点】requests

**Q1：`requests.Session()` 有什么用？**

> 三个：① 自动维持 cookie，登录后后续请求不用手动带；
> ② 复用 TCP 连接（底层用 urllib3 连接池），性能更好；
> ③ 统一设置默认 headers（`s.headers.update(...)`），不用每个请求重复写。
> 用完要 `session.close()`，或者用 `with` 语句。
>
> **加分/防坑**：`Session` **不能**统一设 timeout——
> `s.timeout = 1` 是无效的，requests 不读这个属性。
> 要统一超时得继承 Session 重写 `request`，在里面做
> `kwargs.setdefault("timeout", self._timeout)`。
> （很多面试官会顺着这个追问："那你的框架怎么统一管超时？"）

**Q2：`params`、`data`、`json` 三个参数的区别？**

> `params` 拼到 URL 查询串上（?a=1&b=2），一般 GET 用；
> `data` 放请求体，表单编码（`a=1&b=2`）；
> `json` 放请求体，JSON 编码，并且自动加 `Content-Type: application/json`。
> 用错了服务端解析不到参数，会报"参数缺失"——这是新手最常见的坑。

**Q3：接口依赖（上下游传参）怎么解决？**

> 上游接口响应里用 JSONPath 提取需要的字段，存进全局变量池；
> 下游用例里用 `${变量名}` 占位；发请求前统一做替换。
> 要注意执行顺序和脏数据问题（用例失败时变量可能没设置）。

**Q4：为什么要做数据库校验？**

> 因为接口返回成功不代表数据真的落库了——可能事务回滚、异步失败、只改了缓存。
> 金融类业务（下单、支付、核销）必须做库表校验，这是发现严重 bug 的关键手段。

**Q5：接口返回 200 但业务失败了，你怎么断言？**

> 两层断言：HTTP 状态码 + 响应体里的业务 code。
> 很多系统 HTTP 状态码只表示"请求被处理了"，业务结果要看 code 和 msg。

**Q6：请求超时怎么处理？**

> 必须设 `timeout`，否则服务端不响应会一直挂着。
> 框架里一般设默认超时（比如 10 秒），配合失败重试（比如重试 2 次），
> 仍然失败才算用例失败，并记录日志。

**追问：`timeout=5` 是"总共等 5 秒"吗？**（这题很容易答错）

> **不是。** 它是 connect 和 read 两个独立超时。read 指的是
> "**两次收到字节之间**"的最大间隔，不是整个请求的总时长。
> 所以一个每 1 秒吐一块、总共吐 8 秒的响应，用 `timeout=5` 是拦不住的（实测 8 秒才返回）。
> requests 没有请求级的总时长超时；要控总时长只能在用例层自己计时，
> 或者换 httpx 的 `Timeout(total=...)`。

**Q7：你怎么测一个需要登录才能访问的接口？**

> 用一个全局 fixture 先登录拿 token，存进 Session 的 headers 或者变量池，
> 后续用例共用。token 过期要能自动重新获取。

## 用例设计：其实 mock 里已经给你铺好了

很多人的接口测试用例就是"正向跑一遍、改个参数再跑一遍"。
**真正值钱的是负向用例**，而 mock 里现成准备了 13 个业务错误码和一堆边界
（完整表在 `mock_server/app.py` 的文件头注释里）。照着下面四层设计：

| 层 | 怎么设计 | mock 里现成的素材 |
|---|---|---|
| ① 正向 | 正常参数，校验**两层**（HTTP 状态码 + 业务 code） | 登录成功 / 创建订单成功 / 支付成功 |
| ② 参数校验 | 必填、类型、长度、边界、特殊字符 | username 2–20 位（试 `a` 和 `a*21`）、phone 必须 11 位、amount > 0、page/size 必须正整数 |
| ③ 异常场景 | 不存在的 id、重复提交（幂等）、状态非法 | 用户不存在 2001、订单不存在 3003、**重复支付 3004**（幂等保护）、过期时间戳 4002 |
| ④ 安全 | 不带 token、token 无效、签名错误 | 401（无 token）、签名错误 4003、**错误密钥算的签名也要被拒** |

> **这四层就是面试官问"你怎么做接口测试用例设计"时的标准答案**——
> 但你必须能举出具体例子。上面每一格都能在 mock 上真的跑一遍，
> 光这一点就比"我一般从正向、异常、边界几个角度设计"强得多。
>
> 第 ④ 层特别是加分项：本项目 Day4 框架里**真的有无 token 的 401 用例**
> （`data/test_user.yaml`、`data/test_order.yaml` 各一条），
> 被追问时能直接翻出来。
