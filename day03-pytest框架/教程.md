# 一、pytest vs unittest

Python 有两个主流测试框架。

| | unittest（内置） | pytest（第三方，主流） |
|---|---|---|
| 用例写法 | 必须继承 `TestCase` 类 | 普通函数就行 |
| 断言 | `self.assertEqual(a, b)` | 直接 `assert a == b` |
| 前后置 | `setUp` / `tearDown` | fixture + yield，更灵活 |
| 参数化 | 要 `ddt` 或 `subTest` | 内置 `@pytest.mark.parametrize` |
| 插件生态 | 少 | 极丰富 |
| 失败信息 | 只有"不相等" | 会显示变量的实际值 |

**结论：现在新项目基本都选 pytest。** 但你要知道 unittest，因为老项目和面试官可能问。

## 1.1 为什么 pytest 直接 assert 就行

unittest 必须用 `self.assertEqual(a, b)`，pytest 直接 `assert a == b`，而且失败信息还更详细。

原因：pytest 有个"断言重写"机制——**它在导入测试模块时，会改写 `assert` 语句**，让它失败时把相关变量的值都记录下来。

```python
def test_demo():
    a = "hello"
    b = "world"
    assert a == b
```

失败时 pytest 显示：
```
E   AssertionError: assert 'hello' == 'world'
E     - world
E     + hello
```

变量的值直接给你看，不用自己写 message。

# 二、用例怎么写

## 2.1 命名规则（必须遵守，不然收集不到）

pytest 默认只收集：

- **文件**：`test_*.py` 或 `*_test.py`
- **函数**：`test_*` 开头的函数
- **类**：`Test*` 开头的类（且不能有 `__init__` 方法）
- **类里的方法**：`test_*` 开头

```python
# test_demo.py

def test_login():          # ✓ 会被收集
    pass

def login_test():          # ✗ 不会被收集（不是 test_ 开头）
    pass

class TestUser:            # ✓ 会被收集
    def test_get(self):    # ✓ 会被收集
        pass
    def get_user(self):    # ✗ 不会被收集
        pass
```

**最常见的坑**：文件名写了 `user_test.py` 或 `demo.py`，跑 pytest 时提示"collected 0 items"。

## 2.2 最简用例

```python
def test_add():
    assert 1 + 1 == 2
```

运行：

```bash
pytest                        # 跑当前目录所有
pytest test_demo.py           # 跑指定文件
pytest test_demo.py::test_add # 跑指定用例
pytest -v                     # 详细模式，显示每个用例名
pytest -s                     # 显示 print 输出（默认会捕获）
pytest -k "login"             # 只跑名字里含 login 的
```

> `-s` 和 `-v` 是最常用的两个，调试时用 `pytest -vs`。

## 2.3 结果符号

```
.  通过 (passed)
F  失败 (failed)
E  报错 (error，通常是 fixture 或用例外的代码出错)
s  跳过 (skipped)
x  预期失败 (xfailed)
X  意外通过 (xpassed)
```

# 三、fixture（核心）

## 3.1 fixture 解决什么问题

需求：多个用例都要先登录拿 token。

笨办法：每个用例里都写一遍登录代码。
重复、且登录接口一改要改 N 处。

fixture 的作用：**把"准备数据"和"清理数据"抽出来，谁需要谁用。**

## 3.2 基本用法

```python
import pytest

@pytest.fixture
def token():
    """定义一个 fixture：登录并返回 token"""
    print("登录中...")
    t = "mock_token_abc123"
    return t

def test_get_user(token):        # 参数名 = fixture 名，pytest 自动注入
    print(f"用 {token} 查用户")
    assert token is not None
```

**关键**：用例的参数名 `token` 和 fixture 函数名一致，pytest 就会自动把 fixture 的返回值传进去。
**不需要 import，不需要调用**（写 `token()` 反而错了）。

## 3.3 用 yield 做前后置（Day 1 的知识）

```python
@pytest.fixture
def user():
    print("① 创建测试数据")        # setup
    data = {"id": 1, "name": "test"}
    yield data                     # 把数据交给用例
    print("③ 清理测试数据")         # teardown

def test_user(user):
    print(f"② 用例使用 {user}")
```

执行顺序：
```
① 创建测试数据
② 用例使用 {'id': 1, 'name': 'test'}
③ 清理测试数据
```

**这就是 Day 1 讲 yield 的意义**——它把一个函数劈成前后两半。
用 `return` 的话，清理代码永远执行不到。

> 重要：即使用例**失败**了，yield 之后的清理代码**依然会执行**。
> 这是 pytest 保证的，所以可以放心用 fixture 做数据清理。

## 3.4 作用域 scope

问题：每条用例都登录一次，100 条用例就登录 100 次，慢且没必要。

`scope` 控制 fixture 多久创建一次：

| scope | 什么时候执行 | 典型用途 |
|---|---|---|
| `function`（默认） | 每个用例一次 | 用例间互不影响的数据 |
| `class` | 每个测试类一次 | 类内共享 |
| `module` | 每个 .py 文件一次 | 模块级共享 |
| `package` | 每个包一次 | |
| `session` | 整个测试过程一次 | **登录 token、数据库连接** |

```python
@pytest.fixture(scope="session")
def token():
    print("只登录一次")
    t = do_login()
    yield t
    print("全部跑完才退出登录")
```

**实战建议**：登录 token 用 `session` 级（快），每条用例的独立数据用 `function` 级（隔离）。

**坑**：`session` 级 fixture 被 `function` 级用例共享，如果用例改了它，会污染其他用例。
所以共享的东西要保证只读，或者用完恢复。

## 3.5 conftest.py：共享 fixture

问题：多个测试文件都要用 `token` fixture，难道每个文件都定义一遍？

`conftest.py` 是 pytest 的**特殊文件**，它里面定义的 fixture 对**同级及子目录的所有用例**自动可见，不需要 import。

```
day03-pytest框架/
├── conftest.py          ← 放公共 fixture
└── code/
    ├── test_api.py      ← 直接用 token，不用 import
    └── test_order.py    ← 也能用
```

```python
# conftest.py
import pytest

@pytest.fixture(scope="session")
def token():
    ...
```

**要点**：
- 文件名必须是 `conftest.py`，不能改
- 可以有多个（每个目录一个），子目录的优先级更高
- **不需要 import**，pytest 自动加载

## 3.6 fixture 之间的依赖

fixture 可以用别的 fixture：

```python
@pytest.fixture(scope="session")
def token():
    return do_login()

@pytest.fixture
def api_client(token):        # 依赖 token
    s = requests.Session()
    s.headers.update({"token": token})
    return s

def test_get_user(api_client):   # 用 api_client
    api_client.get(...)
```

pytest 会先解析 `token`，再创建 `api_client`。**依赖链自动处理**。

## 3.7 autouse：不用声明也生效

```python
@pytest.fixture(autouse=True)
def print_separator():
    print("\n" + "=" * 50)
    yield
```

`autouse=True` 的 fixture 会被**同作用域的所有用例自动使用**，不用写参数。

典型用途：自动记录日志、自动计时、每个用例前后打印分隔线。

> 用多了会让用例行为不透明（不知道自己被加了什么），谨慎使用。

# 四、参数化

## 4.1 问题

测登录，要测：正确账号、密码错误、用户名为空、用户名超长……
如果写成 4 个用例，代码几乎一样，只有数据不同。

## 4.2 parametrize

```python
import pytest

@pytest.mark.parametrize("username, password, expect_code", [
    ("admin", "123456", 0),        # 正确
    ("admin", "wrong", 1003),      # 密码错误
    ("", "123456", 1001),          # 用户名为空
    ("a" * 21, "123456", 1002),    # 用户名超长
])
def test_login(username, password, expect_code):
    resp = requests.post(url, json={"username": username, "password": password})
    assert resp.json()["code"] == expect_code
```

一份逻辑，4 条数据，pytest 会生成 4 个用例：

```
test_login[admin-123456-0] PASSED
test_login[admin-wrong-1003] PASSED
test_login[-123456-1001] PASSED
test_login[aaaaaaaa...-123456-1002] PASSED
```

**这就是"数据驱动"的雏形**：逻辑一份，数据在列表里。
Day 4 会把数据挪到 YAML 文件里，做到"改数据不用改代码"。

## 4.3 参数化的两个细节

**参数是字典时**：

```python
@pytest.mark.parametrize("case", [
    {"name": "登录成功", "username": "admin", "expect": 0},
    {"name": "密码错误", "username": "admin", "expect": 1003},
])
def test_login(case):
    print(case["name"])
    assert ...
```

**多重参数化（笛卡尔积）**：

```python
@pytest.mark.parametrize("env", ["test", "prod"])
@pytest.mark.parametrize("user", ["admin", "guest"])
def test_multi(env, user):
    pass
# 会生成 4 条：test/admin, test/guest, prod/admin, prod/guest
```

# 五、标记 mark

## 5.1 跳过

```python
@pytest.mark.skip(reason="功能还没实现")
def test_not_ready():
    pass

@pytest.mark.skipif(sys.platform == "win32", reason="Windows 上不跑")
def test_linux_only():
    pass
```

## 5.2 预期失败

```python
@pytest.mark.xfail(reason="已知 bug，等开发修")
def test_known_bug():
    assert 1 == 2
```

结果标记为 `xfailed`，**不算失败**，不影响整体结果。

> 用于标记"已知问题"，比注释掉用例或删掉要好——问题还在视野里。

## 5.3 自定义标记（分组执行）

```python
@pytest.mark.smoke      # 冒烟
def test_login(): ...

@pytest.mark.slow       # 慢用例
def test_report(): ...
```

运行指定标记：

```bash
pytest -m smoke           # 只跑冒烟
pytest -m "not slow"      # 不跑慢的
```

自定义标记要在 `pytest.ini` 里注册，否则会有警告：

```ini
[pytest]
markers =
    smoke: 冒烟用例
    slow: 慢用例
```

## 5.4 为什么需要分组

实际项目几百条用例，全跑要半小时。
**提交代码时只跑冒烟（1 分钟）**，**晚上跑全量**，这是标准做法。

# 六、断言

## 6.1 基本断言

```python
assert resp.status_code == 200
assert resp.json()["code"] == 0
assert "token" in resp.json()["data"]
```

## 6.2 带提示信息（推荐）

```python
assert resp.json()["code"] == 0, f"期望 code=0，实际 {resp.json()}"
```

失败时会打印你的提示，**排查效率高很多**。框架里养成为每个断言加 msg 的习惯。

## 6.3 断言异常

```python
import pytest

with pytest.raises(ValueError):
    int("abc")

# 还能校验异常信息
with pytest.raises(ValueError, match="invalid literal"):
    int("abc")
```

用于测试"接口参数非法时应该报错"这类场景。

## 6.4 浮点断言

```python
assert abs(a - b) < 0.01        # 金额比较不要用 ==
# 或
assert a == pytest.approx(b)    # pytest 提供的近似比较
```

# 七、常用插件

在 `requirements.txt` 里已经列好了，装了就能用。

| 插件 | 作用 | 用法 |
|---|---|---|
| `pytest-html` | 生成 HTML 报告 | `pytest --html=report.html` |
| `pytest-rerunfailures` | 失败自动重试 | `pytest --reruns 2` |
| `pytest-xdist` | 并发执行 | `pytest -n 4`（4 个进程）⚠️ 前提见下 |
| `pytest-ordering` | 控制执行顺序 | `@pytest.mark.run(order=1)` |
| `allure-pytest` | Allure 报告（最漂亮） | `pytest --alluredir=./allure-results` |

**面试高频**：

**Q：用例偶尔失败（不稳定），你怎么处理？**
> ① 先排查是不是用例本身的问题：接口依赖没做、数据没清理、有并发冲突
> ② 确认是环境抖动的话，加失败重试（`--reruns 2`），重试还失败才算真失败
> ③ 但重试不能滥用——它会掩盖真实问题。我会把频繁需要重试的用例单独标记出来跟进

**Q：用例多跑得慢怎么办？**
> 用 `pytest-xdist` 并发执行（`pytest -n auto`）。
> 前提是用例之间没有依赖、不共享可变数据，否则并发会互相干扰。
> 另外可以分层：提交时只跑冒烟，全量放晚上跑。

⚠️ **补一句具体现象，面试说出来更可信**：
> xdist 的 `-n` 是**开进程**不是开线程，每个 worker 有自己的内存。
> 所以如果用例之间靠全局变量传数据（上一条提取、下一条用），
> 并发时两条用例落在不同进程，就会取不到值、直接报 KeyError。
> 这种情况要么把依赖数据放外部存储，要么把跨模块的链路写成一条自包含用例。

（Day 4 的框架正好撞上这个问题，那里有完整分析。）

# 九、实战：把 Day 2 的脚本改成 pytest 用例

对比一下改造前后。

**改造前（Day 2 的脚本）**：

```python
s = requests.Session()
resp = s.post(url + "/api/login", json={...})
token = resp.json()["data"]["token"]
s.headers.update({"token": token})

resp = s.get(url + "/api/user/1")
if resp.json()["code"] != 0:
    print("失败")
else:
    print("通过")
```

问题：没断言（只是 print）、失败不会中断、没有报告、多条用例要复制粘贴。

**改造后**：

```python
# conftest.py
@pytest.fixture(scope="session")
def api():
    s = requests.Session()
    r = s.post(f"{BASE_URL}/api/login",
               json={"username": "admin", "password": "123456"})
    s.headers.update({"token": r.json()["data"]["token"]})
    yield s
    s.close()

# test_user.py
@pytest.mark.parametrize("uid, expect_code", [
    (1, 0),
    (99999, 2001),
])
def test_get_user(api, uid, expect_code):
    r = api.get(f"{BASE_URL}/api/user/{uid}")
    assert r.status_code == 200, f"HTTP 状态码异常：{r.status_code}"
    assert r.json()["code"] == expect_code, f"业务 code 不符，响应：{r.text}"
```

完整代码在 `code/test_api.py` 和 `conftest.py`，跑一遍看效果：

```bash
cd day03-pytest框架
pytest -vs
```

# 十、【面试考点】pytest

**Q1：fixture 的 scope 有哪几种？分别什么时候用？**

> `function`（默认，每个用例一次）、`class`（每个类一次）、`module`（每个文件一次）、
> `package`（每个包一次）、`session`（整个测试过程一次）。
> 登录 token 和数据库连接用 session，避免每条用例重复创建；
> 用例专属的测试数据用 function，保证用例之间互不影响。

**Q2：fixture 怎么做前后置？为什么用 yield 不用 return？**

> yield 之前是 setup，yield 之后是 teardown。
> 用 return 的话函数直接结束，清理代码执行不到。
> 而且 pytest 保证**即使用例失败，teardown 也会执行**，所以适合做数据清理。

**Q3：conftest.py 是干嘛的？**

> 放公共 fixture 和钩子的特殊文件，对它所在目录及子目录的所有用例生效，
> 用例里不用 import 就能直接用。可以有多个，子目录优先级更高。

**Q4：pytest 和 unittest 的区别？**

> ① pytest 用例是普通函数，不用继承类，写起来更简洁
> ② pytest 直接用 assert，失败信息还会显示变量值（靠断言重写机制）
> ③ pytest 的 fixture 比 setUp/tearDown 灵活，支持 5 种作用域和依赖注入
> ④ pytest 参数化是内置的，unittest 要靠 ddt
> ⑤ pytest 插件生态丰富（html 报告、失败重试、并发）

**Q5：用例之间怎么解决接口依赖？**

> 用 fixture 依赖：登录 fixture 返回 token，下游 fixture 依赖它。
> 需要跨用例传递的动态值（比如新建的订单 id），存到变量池。
> 但要注意执行顺序——pytest 默认按文件中的定义顺序执行，跨文件依赖不可靠，
> 所以**不要让用例之间产生强依赖**，最好每条用例自己准备数据。

**Q6：怎么只跑一部分用例？**

> `pytest -m smoke` 按标记跑；`pytest -k "login"` 按名字匹配；
> `pytest path/to/test_x.py::test_y` 精确指定。

**Q7：失败重试会不会掩盖问题？**

> 会。如果只是加 `--reruns` 而不跟进，真实的偶现 bug 就被藏起来了。
> 我的做法是：重试只用于环境抖动，重试通过的用例单独统计出来定期审查，
> 连续多次需要重试的用例要重点排查（多半是用例设计有问题）。
